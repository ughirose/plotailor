##### 1. モバイルセーフなアトミック書き込み処理（safeAtomicWrite の改善）
import { DataAdapter, Platform } from 'obsidian';export class MobileResilientStorage {  constructor(private adapter: DataAdapter, private filePath: string) {}  async writeSafe(content: string): Promise<void> {    const tempPath = `${this.filePath}.tmp`;    // 書き込むJSON文字列自体の妥当性を事前検証    try {      JSON.parse(content);    } catch (e) {      throw new Error(`[Worldcraft] 不正なJSONデータのため書き込みを中断しました: ${e}`);    }    try {      // 1. 一時ファイルへの書き込み      await this.adapter.write(tempPath, content);      // 2. モバイル環境特有の置換処理      if (Platform.isMobile) {        // iOS等では既存ファイルを明示的に削除してからrenameする方が安全        if (await this.adapter.exists(this.filePath)) {          await this.adapter.remove(this.filePath);        }        await this.adapter.rename(tempPath, this.filePath);      } else {        // デスクトップ環境では標準的な置換を試みる        try {          await this.adapter.rename(tempPath, this.filePath);        } catch {          if (await this.adapter.exists(this.filePath)) {            await this.adapter.remove(this.filePath);          }          await this.adapter.rename(tempPath, this.filePath);        }      }      // 3. 書き込み後の完全性検査（サイズとパース確認）      const verifyContent = await this.adapter.read(this.filePath);      if (verifyContent.length === 0) {        throw new Error('[Worldcraft] 書き込み後のファイルサイズが0バイトです。');      }    } catch (error) {      // ロールバック: 一時ファイルのクリーンアップ      if (await this.adapter.exists(tempPath)) {        await this.adapter.remove(tempPath).catch(() => {});      }      throw error;    }  }}

- 書き込み直後のサイズ検査: モバイルOS特有のクラッシュによって「ファイルは作成されたが中身が空」という状態が生じた場合、即座に検知して例外を発報します。

##### 1. バックグラウンド移行時の即時フラッシュ
通常、キーストローク時の保存処理にはデバウンス（例: 500ms〜1000msの遅延）を設けますが、ユーザーがアプリを閉じる動作をした瞬間にキューを強制消化するハンドラーを登録します。
// src/main.ts 内でのライフサイクル監視import { Plugin } from 'obsidian';export default class WorldcraftPlugin extends Plugin {  async onload() {    // ObsidianのワークスペースおよびDOMのpause/blurイベントを購読    this.registerDomEvent(window, 'pagehide', async () => {      await this.flushPendingWrites();    });    this.registerDomEvent(window, 'beforeunload', async () => {      await this.flushPendingWrites();    });    // モバイルネイティブのサスペンド検知（Cordova/Capacitor互換イベント）    this.registerDomEvent(document, 'pause', async () => {      await this.flushPendingWrites();    });  }  private async flushPendingWrites(): Promise<void> {    // 保留中のデバウンスタイマーを解除し、現在のインメモリ状態を同期的に保存パイプラインへ流す    if (this.isDirty) {      console.log('[Worldcraft] サスペンドを検知。未保存の伏線データを即時フラッシュします。');      await this.storage.save(this.currentNodes);      this.isDirty = false;    }  }}

#### 6. 自律的な立場からの検証：抽出精度における潜在的課題
この抽出ルールを実装するにあたり、以下の技術的・表現的な難点についてあらかじめ考慮しておく必要があります。
- 叙述トリック・比喩表現の誤検知 例えば「彼の心には冷たい石が沈んでいた」という文学的・比喩的な表現に対し、ルールや単純な推論が「アイテム: 冷たい石」として拾ってしまう誤判定のリスクが存在します。
  - 対策: プロンプトの除外基準に「物理的に存在しない比喩・心理描写の具象化表現を厳禁とする」旨を明記し、重要度判定において「他者との授受」「物理的接触（持つ、抜く、拾う等）」を伴う動詞との結合度を重視するバリデーションが有効と考えられます。
- 作風（ジャンル）ごとの重要度の乖離 ハイファンタジーでは「魔導具や家名」が極めて重要ですが、現代ドラマや純文学では「ある日の喫茶店のレシート」や「交わした視線」が重大な伏線になります。ジャンルごとの重要度基準のズレに対応するため、プロジェクト設定で「現代・日常系」「ファンタジー・戦記系」「ミステリー系」といった抽出感度プリセットを選択可能にしておく設計が望ましいと推察されます。

#### 各要素の具体的な仕組みと価値の検証
##### 1. 表記ゆれ・用語ガード（世界観レギュレーションの自動化）
Web小説の長期連載や書籍化作業において、最も時間を奪われやすい作業の一つが「用語や漢字の統一（校正）」です。
- 仕組み: マインドマップやグラフに「正式名称: 魔導石」「別名・俗称: 蒼い石」と登録されている場合、本文中に「魔道石」や「魔トウ石」と書かれた瞬間に検知します。
- 技術的裏付け: すべての登録ノード名をメモリ上でトライ木（Aho-Corasick法等）に保持しておくことで、数万文字の原稿に対してもミリ秒単位で完全一致・曖昧一致（レーベンシュタイン距離）を計算でき、LLMを介さずに完全ローカルで動作させることが可能です。
- 作家のメリット: 推敲時に用語集と原稿を往復する手作業が不要になり、執筆中の集中力を削がずに済みます。
##### 2. POV（視点）逸脱検知（カメラワークの厳密化）
小説のクオリティを左右する重要な技法に「視点（Point of View）の固定」がありますが、特に執筆経験が浅い作家や長編連載では、意図せず「主人公の視点なのに、敵の心境を語ってしまう（神の視点への混線）」という構図の破綻が起きやすいと推察されます。
- 仕組み: シーンのメタデータに pov: "char_alicia" と設定されている場合、アリシアの視界外の情報（例: 「背後で男は冷酷な笑みを浮かべていた」「男の胸中は怒りに燃えていた」）を検出した際に、インラインで注記を出します。
- 技術的裏付け: 前述の「主観認識層（アリシアが知覚可能な情報範囲）」と、構文解析（知覚動詞「見る」「聞く」と対象の係り受け）を突き合わせることで、破綻の可能性が高い文章を特定します。
##### 3. ペーシング・感情曲線のビジュアルアナリティクス
商業作品や人気Web小説では、「起承転結の波（カタルシス）」や「会話と情景描写の比率」が読者の離脱率（読了率）に直結します。
- 可視化の具体例:
  - キャラクター登場ヒートマップ: 「ヒロインが第15話から第30話まで一度も登場していない」といった偏りを一目で把握。
  - テキスト密度・会話率: 各話の「カギ括弧の割合」を棒グラフ化し、「説明ゼリフばかりの重い回」「会話だけのスカスカな回」を客観的に検知。
- 作家のメリット: 自分の感覚だけに頼らず、「そろそろ読者を惹きつける山場（イベント）を入れるべきタイミングか」を客観的な指標に基づいて判断しやすくなります。
##### 4. 没プロット・IF分岐箱（非破壊的な設定実験）
プロットを推敲する際、「この事件で仲間を助けるルートと、見捨てるルートのどちらが面白くなるか」を試行錯誤したいという強い欲求が存在します。しかし、既存のツールでは設定を書き換えると元に戻すのが困難になる傾向があります。
- 仕組み: メインの世界観（正史）からワンクリックで「IF世界線」を分岐させます。IFルート内での変更（例: キャラの死亡フラグを反転させる）はメイングラフには影響を与えず、どちらのプロットを採用するか決まるまで並行して保持できます。
- 作家のメリット: 「設定を壊してしまう恐怖」を感じることなく、大胆なストーリー展開の実験を安心して行える心理的安全性が確保されます。
#### ビジネス価値（ROI）とプロダクトポジショニングの検証
これらの要素を追加することが、Worldcraftの事業性や競争力にどのような影響を与えるかを考察します。
- 「書籍化・商業作家」へのターゲット拡大（LTVの向上） 趣味の連載作家だけでなく、レーベルから出版を目指す作家や既に商業デビューしているプロにとって、「表記ゆれの撲滅」や「POVの厳格化」は編集者からの修正依頼（リテイク工数）を劇的に減らす実務的ROIを持ちます。この層は月額課金に対する支払意欲（Willingness to Pay）が比較的高いため、有料プランの主要な訴求軸になり得ます。
- 競合エディタに対する「非侵略的」な優位性 これらの機能は、本文エディタを自作して囲い込む必要がなく、前述の「Obsidian等の外部エディタの横に置くコンパニオン」や「Markdownファイルを読み込んで分析する静的解析ツール」として提供可能です。競合ツールとの摩擦を避けつつ、プラグインとしての導入率を高めやすいと考えられます。

これらの要素を一度に盛り込もうとすると、開発リソースが分散し、MVPのリリースが遅れるリスクが生じます。実装難易度とユーザー体感価値から見た優先順位を検討する必要があります。

#### 5. 自律的な立場からの検証：日本語執筆特有の課題と対抗策
IDEの体験をそのまま日本語の小説執筆に移植しようとする場合、アルファベット圏のコード記述とは異なる「日本語特有の構造的課題」が存在するため、慎重な調整が必要と考えられます。
- 課題A：IME変換候補ウィンドウとの「二重ポップアップ」衝突 日本語入力では、未確定文字列に対してOS標準のIME（ATOK、Google日本語入力、MS-IME等）が変換候補を表示します。この状態でエディタ側がオートコンプリート窓を重ねて表示すると、画面が乱雑になり執筆の著しい妨げとなります。
  - 対策: compositionstart および compositionend イベントを厳密に監視し、「IMEの変換確定（Enter押下）が行われるまで補完ポップアップを抑制する」、あるいは「@ 等の半角記号をトリガーとした場合のみ即時展開する」といった入力モードの住み分けが必須になると推察されます。
- 課題B：ルビや助詞による誤検知（過度な警告のストレス） 例えば「アリシアは」という文に対し、助詞の「は」まで含めて「アリーシアと似ている」と誤検知して波線を出すと、作家にとって大きなノイズになります。
  - 対策: 単純な文字列比較ではなく、形態素解析（kuromoji.js等の軽量ローカルパーサー）を介して「名詞部分のみ」を切り出して辞書照合する、または形態素境界を意識した走査ロジックを組むことが誤判定（False Positive）を減らす鍵になると考えられます。
このように、コードエディタの快適さを取り入れつつ、日本語IMEの邪魔をしない繊細なイベント制御を施すことで、作家が「自分の頭の中の辞書が直接エディタに同期している」ような没入感を得られる可能性が高いと言えます。

#### 1. 用語オートコンプリート拡張の実装仕様
@codemirror/autocomplete を利用し、世界観辞書（人物・用語・アイテム）から候補を提示します。ルビが設定されている場合は、選択時に小説形式（カクヨム・なろう準拠の ｜単語《ルビ》）へスニペット展開できる設計とします。
import {  CompletionContext,  CompletionResult,  snippetCompletion,} from '@codemirror/autocomplete';import { EditorView } from '@codemirror/view';export interface LoreDictionaryEntry {  id: string;  name: string;          // 正式名称（例: "魔導石"）  ruby?: string;         // ルビ（例: "マナストーン"）  category: 'character' | 'term' | 'item';  description?: string;  // 補完窓に表示する短い説明}export function createLoreCompletionSource(dictionary: LoreDictionaryEntry[]) {  return (context: CompletionContext): CompletionResult | null => {    const { state, pos, explicit, view } = context;    // 1. IME入力中（未確定状態）であれば、一切の補完探索を行わない    if (view && (view as EditorView).composing) {      return null;    }    // 2. カーソル直前の単語またはトリガー文字の境界を判定    // パターンA: '@' で明示的に呼び出された場合    const explicitMatch = context.matchBefore(/@[\w\u3040-\u309F\u30A0-\u30FF\u4E00-\u9FFF]*/);    // パターンB: 通常入力（2文字以上のカタカナまたは漢字）    const implicitMatch = context.matchBefore(/[\u30A0-\u30FF\u4E00-\u9FFF]{2,}/);    const match = explicitMatch || (explicit ? implicitMatch : null);    if (!match) return null;    // 先頭の '@' を除去した検索クエリ    const query = match.text.startsWith('@') ? match.text.slice(1) : match.text;    // 3. 辞書ノードとのプレフィックス・部分一致検索    const matchedEntries = dictionary.filter((entry) =>      entry.name.toLowerCase().includes(query.toLowerCase())    );    if (matchedEntries.length === 0) return null;    return {      from: match.from,      options: matchedEntries.map((entry) => {        // ルビが存在する場合はスニペットとして展開（Tabでカーソル移動可能）        if (entry.ruby) {          return snippetCompletion(`｜${entry.name}《${entry.ruby}》#{cursor}`, {            label: entry.name,            detail: `[${entry.ruby}] ${entry.category}`,            info: entry.description,            type: entry.category,          });        }        return {          label: entry.name,          detail: entry.category,          info: entry.description,          type: entry.category,        };      }),    };  };}
#### 2. 表記ゆれLinter拡張の実装仕様
@codemirror/lint を利用し、正式名称に対して登録された「既知の誤記」や、近似した表記ゆれを検知して波線を表示します。クイックフィックス（ワンクリック置換）にも対応させます。
import { Diagnostic, linter } from '@codemirror/lint';import { EditorView } from '@codemirror/view';export interface TermRegulation {  canonical: string;       // 正式表記（例: "魔導石"）  forbidden: string[];     // 禁止・誤表記（例: ["魔道石", "魔トウ石"]）  category: string;}export function createLoreLinter(regulations: TermRegulation[]) {  return linter(    (view: EditorView): Diagnostic[] => {      // 1. IME未確定中はリントを完全にバイパス（誤判定波線の抑止）      if (view.composing) {        return [];      }      const diagnostics: Diagnostic[] = [];      const doc = view.state.doc;      const text = doc.toString();      // 2. 登録された誤表記パターンを高速走査（本文全体から検索）      for (const reg of regulations) {        for (const wrongTerm of reg.forbidden) {          let index = text.indexOf(wrongTerm);          while (index !== -1) {            const from = index;            const to = index + wrongTerm.length;            diagnostics.push({              from,              to,              severity: 'warning',              message: `【表記ゆれ】正式設定は「${reg.canonical}」です（現在: ${wrongTerm}）`,              actions: [                {                  name: `「${reg.canonical}」に修正`,                  apply(view, from, to) {                    view.dispatch({                      changes: { from, to, insert: reg.canonical },                    });                  },                },              ],            });            index = text.indexOf(wrongTerm, to);          }        }      }      return diagnostics;    },    {      // 打鍵終了後、一定の静止時間（デバウンス）を置いてから走査      delay: 400,    }  );}

#### 自律的な立場からの検証：実運用における潜在的トレードオフ
本実装を長期運用するにあたっては、以下の挙動について配慮しておく必要があると考えられます。
- 長大原稿における単純 indexOf の探索負荷 上記の実装例では簡易的に text.indexOf() を回していますが、十万文字を超える単一ファイルにおいて数十〜数百の用語を同時に走査すると、CPU使用率が跳ね上がるリスクがあります。
  - 対策: 本番導入時は、正規表現または Aho-Corasick法（複数文字列検索アルゴリズム） を採用し、テキスト走査を1パス（O(N+M)）で終わらせるメモリ内インデックス構造へ移行させることが推奨されます。
- 意図的な表記ゆれ（キャラクターの言い間違い等）への配慮 作中の人物が「わざと間違った呼び方をしている」「方言や砕けた口調で呼んでいる」シーンにおいて、機械的にエラー波線が出続けるとノイズになり得ます。LinterのDiagnosticアクションに「この箇所を無視する」または「この章では警告しない」といった例外登録（Suppress）機能を設けておくことが、作家の表現の自由を阻害しないための重要な安全弁になると推察されます。

User prompt: Worldcraftの表記ゆれLinterにおいて、十万文字以上の長編原稿でもCPU負荷をかけずにサブミリ秒で複数用語を走査できる、Aho-Corasick法を用いたTypeScript実装を詳しく検討したいです。
Response: Aho-Corasick法は、検索対象となるすべての用語パターン（禁止語・誤表記語）から事前に有限状態オートマトン（Trie木＋失敗遷移リンク）を構築することで、本文の長さ N とマッチ数 Z に対して O(N+Z) の線形時間走査を実現するアルゴリズムです。
一般的なナイーブ実装（用語ごとに indexOf や正規表現を繰り返し実行する方式）では、用語数 K と本文長 N に対して最悪計算量が O(K×N) に膨らむため、10万文字の原稿で数百語をチェックする場合に数十〜数百ミリ秒のCPUブロッキングが発生し得ます。Aho-Corasick法を採用することで、テキストの長さに依存する走査ステップを1パスに抑え、執筆中の打鍵感を損なわないサブミリ秒〜数ミリ秒台での判定が期待できます。
#### 計算量と実行効率の比較検証
長編小説の原稿（10万文字〜20万文字）に対し、500件の世界観用語（正式表記と誤表記のペア）を照合する場合の挙動予測は、下表のように整理できると考えられます。

| 照合方式 | 走査計算量 | 10万文字・500語での実測想定 | メモリフットプリント | 特徴とトレードオフ |
| --- | --- | --- | --- | --- |
| ナイーブ走査  （用語ごとの indexOf） | O(K×N) | 約 30ms 〜 120ms  （打鍵遅延が発生しやすい） | 最小（追加構造なし） | 単純だが用語数や文字数の増加に比例して遅延が線形悪化する |
| 単一正規表現  （`/(word1 | word2 | ...)/g`） | 不定（エンジン依存） | 約 15ms 〜 60ms |
| Aho-Corasick法  （決定性オートマトン） | O(N+Z)  ※本文長＋出現数 | 約 1.5ms 〜 4ms  （フレームレートを維持） | 中（Trieノード群を保持） | 辞書構築に O(M) を要するが、一度作れば本文走査は極めて低遅延で安定 |

#### 1. Aho-CorasickオートマトンのTypeScript実装
日本語の全角文字（漢字・ひらがな・カタカナ）を安全に処理するため、文字コード単位（char）をキーとする Map を用いて遷移を管理し、幅優先探索（BFS）で失敗リンク（Failure Link）および辞書リンク（Dictionary/Output Link）を構築する構成案です。
// src/linter/ahoCorasick.tsexport interface MatchResult {  from: number;         // 本文内の開始インデックス（0-indexed）  to: number;           // 本文内の終了インデックス（exclusive）  pattern: string;      // マッチした誤表記文字列  canonical: string;    // 正式表記（置換先）}export interface TermRule {  forbidden: string;    // 検出したい誤記・表記ゆれ（例: "魔道石"）  canonical: string;    // 正式名称（例: "魔導石"）}class TrieNode {  // 子ノードへの遷移テーブル  children: Map<string, TrieNode> = new Map();  // 照合失敗時の遷移先（KMPのnext配列に相当）  fail: TrieNode | null = null;  // このノードで一致が確定するルール群（複数ヒット対応）  outputs: TermRule[] = [];}export class AhoCorasickEngine {  private root: TrieNode = new TrieNode();  constructor(rules: TermRule[]) {    this.buildTrie(rules);    this.buildFailureLinks();  }  // 1. Trie木の構築  private buildTrie(rules: TermRule[]): void {    for (const rule of rules) {      if (!rule.forbidden) continue;      let current = this.root;      for (const char of rule.forbidden) {        let nextNode = current.children.get(char);        if (!nextNode) {          nextNode = new TrieNode();          current.children.set(char, nextNode);        }        current = nextNode;      }      current.outputs.push(rule);    }  }  // 2. BFS（幅優先探索）による失敗リンクと出力リンクの構築  private buildFailureLinks(): void {    const queue: TrieNode[] = [];    // 深さ1のノードの失敗先はすべてルートに設定    for (const child of this.root.children.values()) {      child.fail = this.root;      queue.push(child);    }    while (queue.length > 0) {      const current = queue.shift()!;      for (const [char, childNode] of current.children.entries()) {        queue.push(childNode);        let fallback = current.fail;        // 失敗先を辿り、同じ文字で遷移可能なノードを探索        while (fallback !== null && !fallback.children.has(char)) {          fallback = fallback.fail;        }        // 遷移先があればそこを、なければルートを失敗先に設定        childNode.fail = fallback ? fallback.children.get(char)! : this.root;        // 出力リンクの併合（部分一致している出力パターンを継承）        if (childNode.fail && childNode.fail.outputs.length > 0) {          childNode.outputs = childNode.outputs.concat(childNode.fail.outputs);        }      }    }  }  // 3. 本文の単一パス走査  public search(text: string): MatchResult[] {    const results: MatchResult[] = [];    let current = this.root;    for (let i = 0; i < text.length; i++) {      const char = text[i];      // 現在のノードから遷移できない場合、失敗リンクを辿る      while (current !== this.root && !current.children.has(char)) {        current = current.fail ?? this.root;      }      current = current.children.get(char) ?? this.root;      // 出力ノードに到達した場合、マッチ結果を記録      if (current.outputs.length > 0) {        for (const rule of current.outputs) {          results.push({            from: i - rule.forbidden.length + 1,            to: i + 1,            pattern: rule.forbidden,            canonical: rule.canonical,          });        }      }    }    return results;  }}
