# 20260921_【構想】UIUX設計と配色方針

## WorldCraftプロジェクトのUI・UX設計と配色方針
https://gemini.google.com/app/486123251b218b37

User prompt: 現在進めているWorldCraftプロジェクトにおけるデザインについて考えたい。 アーキテクチャは別途考えているので、ユーザーの体験的な意味での UI の使い勝手や、色合いの理想的な姿というところを、現状の設計から考える等をしてほしい。
Response: 世界観構築（Worldbuilding）を支援するアプリケーションでは、設定情報の「厳密な構造化・網羅性」と、創作における「流動的な思考・没入感」がトレードオフになりやすい側面があります。UIの使い勝手およびカラーパレットを定義する上でも、ツール自体がユーザーの認知負荷をいかに下げ、創作対象の世界観を邪魔しない環境を提供できるかという観点から検証することが自然と考えられます。
### 1. UIレイアウトと情報構造の検証
世界観構築では、マクロな設定（世界地図、年表、物理・魔法法則）からミクロな設定（個別人物、アイテム、エピソード）まで多層的なデータを扱います。これらを無理なく行き来するためのレイアウト方式について、それぞれの特性と課題を整理します。

| パターン | 主な特徴 | メリット | 潜在的な課題・検証点 |
| --- | --- | --- | --- |
| 3ペイン構成（IDE / ドキュメント型） | 左：階層ツリー・一覧  中央：エディタ  右：属性メタデータ・被リンク | 階層の把握が容易で、設定を参照しながら執筆しやすい | 画面専有面積が大きく、設定同士の有機的なネットワークを空間的に捉えにくい可能性 |
| 無限キャンバス型（ホワイトボード型） | ノードやカードを自由に配置し、矢印やグループ化で接続 | 相関図や勢力図など、非線形なアイデア出しを阻害しない | 設定項目やテキスト量が増大した際に検索性・一覧性が低下しやすい懸念 |
| コンテキスト切替型（ハイブリッド） | 基本はエディタ中心。必要に応じてグラフや年表ビューへ展開 | 執筆への没入感を保ちつつ、全体像の俯瞰も可能 | モード遷移の設計が複雑化し、ユーザーのメンタルモデルに負担をかけるリスク |

ツールの主目的が「設定資料集の整理・アーカイブ」なのか、それとも「執筆やプロット作成をドライブする思考支援」なのかによって、選ぶべき基本構造が変わる可能性が示唆されます。
### 2. 操作体験（UX）における摩擦の低減
世界観構築特有の使い勝手を高めるにあたり、以下の3つのインタラクションが機能するかどうかが論点になり得ます。
- インラインでのエンティティ参照・新規作成執筆中に新しい用語やキャラクターが登場した際、画面を切り替えずに [[用語名]] や @ トリガー等で既存エンティティとリンク、あるいはその場でスタブ（仮作成）できる仕組みが有効と考えられます。ただし、記法に依存しすぎるとGUI主体のライトユーザーにとって学習コストになる側面も考慮する必要があります。
- 構造化入力の強制レベル（スキーマの柔軟性）最初から「年齢」「所属」「能力値」などの厳密なフォーム入力を要求すると、初期の構想段階で創作の手が止まる懸念があります。自由記述のメモから徐々にキー・バリュー形式のメタデータへ昇華できるような、段階的な構造化が適しているか検証の余地があります。
- 双方向リンクとコンテキストプレビューリンクされた用語にマウスオーバーした際、別画面へ遷移することなく要約ポップアップが表示される機能は、文脈の維持に寄与しやすいと推測されます。
### 3. カラーパレットの理想像と役割分担
世界観構築ツールにおける配色は、「ツール自体の世界観」を主張しすぎないことが重要視される傾向にあります。ファンタジー調やサイバーパンク調といった特定の意匠をUI側に持たせてしまうと、ユーザーが構築している作品世界と認知的な衝突を起こすリスクがあるためです。

| 役割 | トーン・設計方針 | 意図と検証ポイント |
| --- | --- | --- |
| 背景・ベース | 低彩度のダークグレー、または落ち着いたオフホワイト | 長時間の作業に伴う眼精疲労を軽減し、ユーザーの描くコンテンツを主役に据える |
| サーフェス（階層表現） | ベースに対してわずかに明度差をつけたニュートラルグレー | ペインやカードの境界線を過度な線描ではなく面（Elevation）で識別させる |
| テキスト・シンボル | 明度100%の白を避け、85%〜90%程度の高コントラストグレー | コントラスト比（WCAG基準）を担保しつつ、長時間のタイピングでの眩しさを抑える |
| 機能的アクセントカラー | 彩度を中程度に抑えたパステル〜ミュートトーン（青、緑、橙など） | 装飾ではなく、エンティティのカテゴリ（人物・地名・組織など）の識別に限定して使用する |

操作用のアクション（保存、作成、選択中状態）に割り当てるプライマリカラーは1色に絞り、データ分類用のサブカラーと明確に役割を分離することで、UI操作と設定内容の混同を防ぎやすくなると考えられます。
ツールが目指す重心が「自由なテキスト記述」寄りなのか、「関係性を重視したナレッジベース」寄りなのかによって、UIの最適な落としどころが変動します。

Response: 世界観構築（Worldbuilding）の支援ツールにおいては、ユーザーが「どのように思考を発展させていくか」という認知的アプローチの違いによって、求められるUIの重心が大きく変動します。
想定されるターゲット層の特性を検証した上で、思考プロセスに沿った利用フロー、具体的な画面構成、および操作仕様の妥当性について考察します。
### 1. ターゲット層の類型と要件の比較
世界観構築を行うクリエイターは、大きく「物語（ナラティブ）先行型」と「体系（システム）先行型」に分かれる傾向があります。単一のUIで両方を満たそうとすると設計が破綻しやすいため、どちらを主軸に据えるか、あるいはどのように共存させるかが論点となります。

| 項目 | 物語先行型（小説家・シナリオライター等） | 体系先行型（TRPG GM・ゲームプランナー等） |
| --- | --- | --- |
| 思考のアプローチ | ボトムアップ（創発的）  シーンやキャラの会話を書きながら、後追いで世界設定を肉付け・回収する。 | トップダウン（構造的）  地理・年表・勢力図・魔法法則などのルールを先に定義し、その箱庭の中で事象を動かす。 |
| UIへの主要求 | ・執筆を中断させない軽量なエディタ  ・文脈を失わないインライン参照  ・未確定要素を曖昧なまま残せる柔軟性 | ・相関図・ツリー構造の可視化  ・属性テーブル（キー・バリュー）の一括管理  ・タイムラインやルール体系の整合性検証 |
| 設計上のリスク | 厳密なスキーマ入力を求められると、思考の勢いが削がれ「データ入力作業」に感じてしまう。 | 自由記述が中心だと、データの関係性が埋もれ、全体の整合性チェックが困難になる。 |

両者のニーズを満たすためには、「最初は自由記述のメモとして書き始め、必要に応じて徐々に構造化されたデータへ昇華できる仕組み」がひとつの現実的な解になると考えられます。
### 2. 創作の進行フェーズ（利用フロー）
世界観構築は直線的に進む作業ではなく、発散と整理の反復です。フローの各段階においてUIが担うべき役割を整理します。
[フェーズ1: 着想・メモ] ──> [フェーズ2: 接続・構造化] ──> [フェーズ3: 俯瞰・整合性検証]  ・思考速度での記述          ・エンティティ化               ・年表との時系列照合  ・未整理の断片保持          ・双方向リンク/属性付与         ・未定義スタブの回収
- フェーズ1：着想・断片の捕獲（Capture）アイデアが浮かんだ瞬間に、分類やフォルダ配置を気にせず即座に書き留められる状態。UIは極力ミニマルであり、入力の摩擦をゼロに近づける必要があります。
- フェーズ2：エンティティ化と関係性の定義（Connect）テキスト内のキーワードを「人物」「地名」「事象」などの実体（エンティティ）として定義し、他の要素と結びつける段階。ここで初めてメタデータ（属性や所属関係）の付与が促されます。
- フェーズ3：全体像の俯瞰と整合性の検証（Validate）出来上がった設定群を年表、相関図、地図などの視点から俯瞰し、生没年の矛盾や設定の重複がないかを洗い出す段階です。
### 3. 具体的な画面構成案（可変3ペイン構成）
作業コンテキストの切り替えを最小限に抑えるため、画面遷移を伴わない「3ペイン分割 + 連動インスペクター」が有効な構成案として考えられます。
┌──────────────┬──────────────────────────────┬──────────────┐│  左ペイン    │          中央ペイン          │  右ペイン    ││ (ナビゲーション)│        (メインワーク)        │ (インスペクター)││              │                              │              ││ ・階層ツリー  │ [エディタ] / [グラフ] / [年表] │ ・属性シート ││ ・エンティティ│                              │ ・被リンク一覧││   タイプ一覧 │ ・インラインリンク機能       │ ・関連タイム  ││ ・クイック検索│ ・未定義要素のスタブ表示     │   ライン     ││              │                              │              │└──────────────┴──────────────────────────────┴──────────────┘
- 左ペイン（ナビゲーション領域）単なるフォルダツリーだけでなく、「エンティティ種別（人物／国家／技術など）」や「未整理メモ」のスマートフィルタを備えます。幅は折りたたみ可能とし、執筆集中時には非表示にできる設計が適しています。
- 中央ペイン（メインワークスペース）デフォルトはMarkdown/リッチテキストエディタ。上部のビューセレクターにより、同一のデータを「ドキュメント」「相関グラフ」「タイムライン」の各ビューへシームレスに切り替えられるようにします。
- 右ペイン（コンテキスト・インスペクター）中央エディタでカーソルが当たっている、または選択中のエンティティに関する情報（属性一覧、バックリンク、言及されている他ドキュメントの抜粋）を常時表示します。画面を離脱することなく、設定の参照・追記を可能にする狙いがあります。
### 4. 操作仕様（Interaction Specs）の検討課題
使い勝手を大きく左右する具体的な操作仕様について、メリットと潜在的な実装・運用課題を検証します。
#### ① スキーマの漸進的適用（段階的構造化）
- 仕様イメージ:最初はプレーンなテキストとして記述し、右クリックまたはコマンドから「人物テンプレートを適用」を選択すると、右ペインに「生年」「所属」「ステータス」などの属性入力フォームが出現する。
- 検証点:自由度が高い反面、ユーザーがテンプレートを適用する動機づけ（構造化することで得られるメリット：自動年表生成など）が明確に伝わらないと、機能自体が形骸化する懸念があります。
#### ② スタブ（未確定要素）の自動生成
- 仕様イメージ:エディタ内で [[新キャラ名]] と入力した際、その対象ページが未作成であっても破綻せず、「未確定スタブ」として薄いハイライトで表示される。クリック時に初めて「新規ページ作成」「既存エンティティへのエイリアス（別名）設定」を選択できる。
- 検証点:リンク切れを恐れずに思考の赴くまま固有名詞を出せるメリットは大きい一方、誤字や表記揺れによって不要なスタブが乱立しやすいという管理上のトレードオフが存在します。
#### ③ インライン・リファレンス（ホバープレビュー）
- 仕様イメージ:リンクされた単語にカーソルを合わせると、カード形式のポップオーバーが表示され、概要と主要属性、所属組織がプレビューされる。
- 検証点:ポップオーバー内で簡易編集まで行えるようにするか、閲覧のみに絞るかによってUIの複雑度が大きく変わります。編集まで許可した場合、エディタのフォーカス喪失や誤操作のリスクが増加するため、初期はプレビューと「別ペインで開く」ショートカットに留めるのが手堅い可能性があります。
このように、ボトムアップの執筆体験を阻害しない操作感を維持しながら、蓄積された設定をいかに自然に構造化へ誘導できるかが、UI設計における鍵になると考えられます。

### 1. エンティティのデータ構造モデル
世界観の構成要素（人物、国家、出来事、地理、アイテムなど）は、階層構造だけでなく複雑なネットワークを形成するため、ドキュメント指向とプロパティグラフのハイブリッド構造が適していると考えられます。
#### データモデルの選定比較

| 方式 | 構造の概要 | 利点 | 課題・トレードオフ |
| --- | --- | --- | --- |
| 厳密なRDB型 | テーブルごとにスキーマを固定（人物テーブル、国家テーブル等） | 型安全性が高く、クエリや整合性チェックを高速に実行可能 | ユーザーが独自の種別（例：神格、概念、魔導兵器）を自由に追加・拡張しにくい |
| 完全スキーマレス型 | プレーンなMarkdown＋任意のタグ付け | 記述の自由度が最大化され、入力の摩擦が極めて低い | 機械可読性が低く、関係性や時系列の論理検証ロジックを走らせにくい |
| グラフ＆メタデータ型（ハイブリッド） | コア属性＋自由定義プロパティ＋エッジ（関係性）リスト | 共通プロパティで検証を行いつつ、個別設定の自由度を維持可能 | グラフ探索の計算量管理や、未確定な曖昧値（「紀元前数百年頃」等）の正規化が必要 |

#### エンティティのコア・スキーマ案
各エンティティをJSON/YAML互換のオブジェクトとして定義する場合、以下のような共通レイヤーと拡張レイヤーの分離が検討できます。

### 2. 設定矛盾を検知する整合性チェック機能
創作における「矛盾」は、単なる記述ミスである場合と、「意図的な叙述トリック・作中内での風聞・時間移動」など物語上の表現である場合が混在します。そのため、コンパイラのように保存をブロックするのではなく、コードレビューのLinter（静的解析）に近い思想でのアプローチが妥当と推測されます。
#### 検知対象となる論理矛盾の分類

| 分類 | 検知パターン | 検出ロジック例 | 例外処理・特例フラグ |
| --- | --- | --- | --- |
| 時系列（Temporal） | 生没年と行動の逆転 | イベント参加時期が、人物の start（誕生）前、または end（死亡）後にある。 | undead, time_traveler, posthumous_influence 等の特性フラグ |
| 世代・因果（Causal） | 親子の年齢逆転・因果のループ | parent_of の対象が、親の生年より前に誕生している。AがBの原因であり、BがAの原因である循環。 | reincarnation（転生）、養子縁組設定 |
| 空間（Spatial） | 同一時間帯の多重存在 | 同一または重複する日時に、物理的に離れた複数イベントの参加者として登録されている。 | teleportation, clone, projection 等の移動・分身フラグ |
| 包含関係（Topological） | 地理・組織の循環参照 | 地域Aが地域Bを含み、地域Bが地域Cを含み、地域Cが地域Aを含んでいる（循環包含）。 | 原則として非ユークリッド空間等の特殊設定を除き警告対象 |
| 参照不整合（Referential） | 孤立・未定義スタブの長期放置 | 本文内で [[未作成エンティティ]] のまま半年以上更新がない、または別名同士が衝突している。 | 未確定要素リストへの自動集約 |

#### 整合性検証エンジンの動作仕様
- 二段階の実行タイミング
  - リアルタイム・ローカル検証:エディタ編集中、フォーカスが外れたタイミングで「編集対象エンティティと直接接続されている1ホップ以内のノード」のみを対象に即時検証。タイピング遅延を防ぐ設計が適しています。
  - 非同期フルグラフスキャン（「世界監査」機能）:プロジェクト全体をバックグラウンドまたは明示的な実行トリガーで走査し、循環参照や長大なタイムラインの不整合を網羅的に洗い出します。
- 例外の許容機構（ルール抑制アノテーション）作家が意図的に発生させている矛盾に対して、エラーを恒久的に非表示化できる手段が不可欠と考えられます。
  - 例：プロパティに suppress_rules: ["temporal_overlap"] を指定することで、特定の警告をミュートし、「意図した設定」として記録に残す仕様。
- 重大度（Severity）のレベル分け
  - Error: 明らかなシステムエラー（ID重複、不正な日付フォーマット）。
  - Warning: 物理的・論理的矛盾（死亡後の戦闘参加、親子の生年逆転）。

日時表現と通算日（Absolute Day）を相互変換するロジックには、主に「数式除算アプローチ」と「二分探索（Binary Search）アプローチ」が考えられます。

| アプローチ | 概要 | 長所 | 課題・トレードオフ |
| --- | --- | --- | --- |

### 3. 相互変換ロジックの実装例
以下は、通算年と通算日の変換、および日付オブジェクトへのデシリアライズを行うコアエンジンの実装例です。
export class TemporalEngine {  private calendar: CalendarDefinition;  private standardYearDays: number;  constructor(calendar: CalendarDefinition) {    this.calendar = calendar;    // 平年の基本日数を計算    const monthDays = calendar.months.reduce((acc, m) => acc + m.days, 0);    const intercalaryDays = calendar.intercalaryDays.reduce((acc, d) => acc + d.durationDays, 0);    this.standardYearDays = monthDays + intercalaryDays;  }  /**   * 指定した絶対年が閏年かどうか判定   */  public isLeapYear(absoluteYear: number): boolean {    const rule = this.calendar.leapRule;    if (!rule) return false;    if (absoluteYear % rule.interval !== 0) return false;    if (rule.excludeIntervals) {      for (const exc of rule.excludeIntervals) {        if (absoluteYear % exc === 0) return false;      }    }    return true;  }  /**   * 特定の年の総日数を取得   */  public getDaysInYear(absoluteYear: number): number {    let days = this.standardYearDays;    if (this.isLeapYear(absoluteYear)) {      days += this.calendar.leapRule?.bonusDays ?? 0;    }    return days;  }  /**   * Eraの年表記から「絶対年（Epochからの通算年）」へ変換   */  public eraYearToAbsoluteYear(eraId: string, year: number): number {    const era = this.calendar.eras.find((e) => e.id === eraId);    if (!era) throw new Error(`Era not found: ${eraId}`);    if (era.direction === 'ascending') {      const offset = era.hasYearZero ? year : year > 0 ? year - 1 : year;      return era.startAbsoluteYear + offset;    } else {      // 降順（カウントダウン形式）      const offset = era.hasYearZero ? year : year - 1;      return era.startAbsoluteYear - offset;    }  }  /**   * 日付オブジェクトから「通算絶対日（Absolute Day）」へのシリアライズ   */  public dateToAbsoluteDay(date: CalendarDate): number {    const absoluteYear = this.eraYearToAbsoluteYear(date.eraId, date.year);        // 1. エポック年（0年）から対象年までの累積日数を計算    // ※ 実運用では、長大な歴史向けに数百〜数千年のブロック単位の事前集計テーブル参照が有効    let days = 0;    if (absoluteYear >= 0) {      for (let y = 0; y < absoluteYear; y++) {        days += this.getDaysInYear(y);      }    } else {      for (let y = -1; y >= absoluteYear; y--) {        days -= this.getDaysInYear(y);      }    }    // 2. 年内の月・日・祝祭日の累積日数を加算    let dayOfYear = 0;    const isLeap = this.isLeapYear(absoluteYear);    const targetMonth = date.monthIndex ?? 1;    for (const m of this.calendar.months) {      if (m.index < targetMonth) {        dayOfYear += m.days;        // 閏月処理        if (isLeap && this.calendar.leapRule?.targetMonthIndex === m.index) {          dayOfYear += this.calendar.leapRule.bonusDays;        }        // 途中の月外祝祭日を加算        const interDays = this.calendar.intercalaryDays          .filter((d) => d.afterMonthIndex === m.index)          .reduce((acc, d) => acc + d.durationDays, 0);        dayOfYear += interDays;      }    }    // 日の加算 (1始まりのインデックスを0始まりに補正)    if (date.day !== undefined) {      dayOfYear += (date.day - 1);    }    return days + dayOfYear;  }  /**   * 通算絶対日（Absolute Day）から日付表現へのデシリアライズ   */  public absoluteDayToDate(absoluteDay: number, preferredEraId?: string): CalendarDate {    // 1. 年の推定と二分探索による特定    let estimatedYear = Math.floor(absoluteDay / this.standardYearDays);        // 年の開始絶対日を取得するヘルパー    const getYearStartDay = (year: number): number => {      let d = 0;      if (year >= 0) {        for (let y = 0; y < year; y++) d += this.getDaysInYear(y);      } else {        for (let y = -1; y >= year; y--) d -= this.getDaysInYear(y);      }      return d;    };    let currentYear = estimatedYear;    let yearStartDay = getYearStartDay(currentYear);    // ズレを補正（ステップ探索）    while (yearStartDay > absoluteDay) {      currentYear--;      yearStartDay = getYearStartDay(currentYear);    }    while (yearStartDay + this.getDaysInYear(currentYear) <= absoluteDay) {      currentYear++;      yearStartDay = getYearStartDay(currentYear);    }    // 2. 年内残日数の分配    let remainingDays = absoluteDay - yearStartDay;    const isLeap = this.isLeapYear(currentYear);    let foundMonth = 1;    let foundDay = 1;    for (const m of this.calendar.months) {      let mDays = m.days;      if (isLeap && this.calendar.leapRule?.targetMonthIndex === m.index) {        mDays += this.calendar.leapRule.bonusDays;      }      if (remainingDays < mDays) {        foundMonth = m.index;        foundDay = remainingDays + 1;        break;      }      remainingDays -= mDays;      // 月外祝祭日の判定      const interDays = this.calendar.intercalaryDays        .filter((d) => d.afterMonthIndex === m.index)        .reduce((acc, d) => acc + d.durationDays, 0);      if (remainingDays < interDays) {        // 祝祭日内の日として処理        return this.formatDateOutput(currentYear, undefined, remainingDays + 1, preferredEraId);      }      remainingDays -= interDays;    }    return this.formatDateOutput(currentYear, foundMonth, foundDay, preferredEraId);  }  private formatDateOutput(    absoluteYear: number,    month?: number,    day?: number,    preferredEraId?: string  ): CalendarDate {    // 該当する紀元（Era）を探索    const era = (preferredEraId && this.calendar.eras.find((e) => e.id === preferredEraId)) ||      this.calendar.eras.find(        (e) =>          absoluteYear >= e.startAbsoluteYear &&          (e.endAbsoluteYear === null || absoluteYear <= e.endAbsoluteYear)      ) ||      this.calendar.eras[0];    let yearInEra: number;    if (era.direction === 'ascending') {      const offset = absoluteYear - era.startAbsoluteYear;      yearInEra = era.hasYearZero ? offset : offset >= 0 ? offset + 1 : offset;    } else {      const offset = era.startAbsoluteYear - absoluteYear;      yearInEra = era.hasYearZero ? offset : offset + 1;    }    return {      eraId: era.id,      year: yearInEra,      monthIndex: month,      day: day,    };  }}

このアーキテクチャを採用するにあたり、以下の技術的論点について留意・検証しておく必要があります。
- ループ計算に伴うパフォーマンスの限界上記の単純なループ累積方式（for (let y = 0; y < absoluteYear; y++)）は、紀元前10万年など長大なタイムスケールを扱う場合にメインスレッドをブロックする懸念があります。実運用では、100年単位・1000年単位の累積日数をあらかじめ配列としてキャッシュしておくか、整数の剰余算に基づくルックアップテーブルの併用が有効と考えられます。
- 「0年」の有無によるオフセット誤差天文学的紀年法では0年（西暦0年）が存在しますが、一般的な歴史記述（紀元前1年の翌年は紀元1年）では0年が存在しません。この境界を跨ぐ差分計算で1年のズレが発生しやすいため、hasYearZero フラグによる厳密なオフセット補正が正しく機能するか単体テストでの網羅的な検証が不可欠です。
- 未確定（Fuzzy）日時のソートとインデックス「100年頃（Range: 90年〜110年）」と「105年3月（確定日）」が混在する場合、タイムライン上の表示順を「区間の中心値（Midpoint）」で並べるか、「開始点（Start）」で並べるかによってUI上の整合性が変わります。内部的には sortKey = (startAbsoluteDay + endAbsoluteDay) / 2 などの明確な代表値を定義することが推奨されます。
このように、日付のシリアライズ処理とデシリアライズ処理を通算日（Absolute Day）経由で一元化することで、タイムラインUIや矛盾検知Linterは「単なる整数の大小比較・区間交差判定」として処理可能となり、コードベースの肥大化を抑えやすくなると考えられます。

| 暗黙の現在時（Context Variable） | 環境変数・カレントスコープ（$CURRENT_TIME） | 「夜が明けた」「数時間後」 | type: "context_relative"  scope: "chapter_03_scene_01"  delta: { hours: 8 } |

このモデルの最大の利点は、「アンカーとなる大事件の日程を修正した際、それに紐づく相対イベント群（『その3日前』『翌週』など）が自動的にカスケードして正しい日付へ再計算される」という点にあります。手動ですべての関連イベントを再計算・書き換えする必要がなくなるため、長期的な設定管理の負荷を大幅に下げる効果が期待されます。
### 2. 「推論提案」と「確定値」を分ける二層構造の検証
自然言語の「3日前」というテキストからシステムが日付を自動判定する場合、意図の取り違え（誤推論）が必ず発生します。そのため、「確定値」と「提案値」を明確にステータス分けする設計の妥当性を評価します。
[本文記述: "砦が包囲される3日前"]         │         ▼ (自然言語解析 / ルールベース推論)┌────────────────────────────────────────────────────────┐│ 【推論提案ステータス】(Suggested)                     ││ ・推定アンカー: 「境界砦包囲戦（105年10月2日）」       ││ ・推定算出日: 105年9月29日                             ││ ・確度スコア: 85% (直前段落の言及に基づく)            │└────────────────────────────────────────────────────────┘         │         ├─ [承認 / ピン留め] ──> 【確定値】(Pinned) に昇格         │         └─ [手動補正] ─────────> 別アンカーや別日程を割り当て
#### 二層化によるメリットと留意点
- メリット:
  - 執筆の中断防止: 推論状態のままでもタイムライン上には「ゴースト（半透明の帯）」として仮配置されるため、執筆中にいちいち確定作業を強いられない。
  - 整合性チェックの段階的適用: 確定値同士の矛盾は「Warning（警告）」とし、推論値が絡む矛盾は「Info（提案・確認）」にとどめることで、Linterの誤警告によるストレスを抑制できる。
- 留意点・トレードオフ:
  - 推論提案の数が膨大になった場合、「未確定リスト」が溜まり続け、ユーザーが整理作業に追われる（テクニカルデットならぬ「設定デット」の発生）。
  - 確定値が増えすぎると、逆にアンカー変更時の柔軟性が失われ、依存関係が固定化（Hard-coded）してしまう懸念がある。
### 3. スコープ（名前空間）の概念と循環参照リスク
「3日前」といった相対指定を扱うにあたり、技術的・設計的に最も慎重な検証を要するのが「スコープ（参照範囲）」と「循環依存」の扱いです。
#### ① スコープ（局所変数としての時間）
テキスト内で単に「翌日」と書かれた場合、その参照元（アンカー）は「作中の世界全体の日時」ではなく、通常は「そのシーンや段落の直前に発生した出来事」になります。
- ドキュメント／シーンごとの環境変数:各エピソードや章のヘッダーにメタデータとして scene_base_time（その場面が始まった基準時）を暗黙的に持たせ、シーン内の「数時間後」「翌朝」はそのベース時間からの差分として計算させる階層構造が合理的と考えられます。
#### ② 依存関係の循環（Circular Dependency）
相対表現が増えると、以下のような論理ループが発生するリスクがあります。
- 事象A: 「事象Bの3日前」
- 事象B: 「事象Cの翌日」
- 事象C: 「事象Aの数日後」
この場合、有向非巡回グラフ（DAG: Directed Acyclic Graph）として依存関係を検証し、ループを検知した瞬間に「循環参照により日付が未定になっています」と別メニュー上でフラグを立てる例外ハンドリングが必須になると推測されます。

### 1. 開発者用語がもたらす認知的・心理的摩擦

画面上でユーザーが目にする文言やインジケーターを、より親しみやすく、かつ状況を正確に伝えるデザインへ見直す具体案です。
#### ① 食い違い表示（旧Warning）のトーン＆マナー
- 旧仕様のテキスト（開発者調）:[Warning] 時系列の不整合: char_01 の死亡日時(104年)より後で event_03(105年) が参照されています。
- 改善案のマイクロコピー:「バルガス卿」は104年に亡くなった設定になっていますが、105年の「境界砦の会見」にも名前が登場しています。
- アクションの選択肢:
  - 「どちらかの時期をずらす」
  - 「理由がある（影武者・誤伝など）」
  - 「いまは気にしない」

#### ③ 時間関係の指定（旧アンカー・オフセット）
エディタの右パネルやポップアップで日時を設定する際、数式のような入力欄を排し、会話文に近いUIパーツを採用します。

### 4. 全体体験（UX）におけるスタンスの転換

| 時期の固定  (旧 Pin / Constant) | 🔒（南京錠）  ⚓（重いアンカー） | 押しピン（プッシュピン）  または 栞留め | 南京錠は「編集ロック・権限エラー」を誤認させやすいため、掲示板にメモを留めるような軽量なピンの造形が分かりやすいと考えられます。 |
| 時間の相対関係  (旧 Relative / Offset) | ⟲（更新矢印）  ±（プラスマイナス） | 波打つ目盛り  または 連なる足跡 | 数式的な記号を避け、ある出来事から歩数を数えるような連続性・間隔を感じさせる意匠が親しみやすいと推測されます。 |

### 3. トーン＆マナーとスタイルガイドの検証
アイコンやコピーを具体化する際、UI全体の一貫性と世界観への中立性を維持するための留意点を整理します。
【スタイル設計の目安】・線の太さ: 1.5px 〜 2px の均一なアウトライン（角はわずかに丸みを持たせる）・色彩設計: 警告色として原色の赤・黄色を避け、くすんだアンバー（琥珀色）や薄いセージグリーンを採用・表示原則: 初出時や主要な操作箇所では「アイコン単体」を避け、短い言葉を併記する
- 過度な「特定世界観」の排除羊皮紙風の巻物、羽ペン、魔法陣といった過度にファンタジー調のモチーフや、逆に基板やサイバー風の意匠を採用すると、異なるジャンル（SF、現代伝奇、歴史物など）を執筆するユーザーにとって視覚的なノイズになるリスクがあります。道具としての普遍性を持つ、ニュートラルでミニマルな線画表現にとどめるのが手堅いアプローチと考えられます。
- アイコンの認知度とテキスト併記のバランスパズルのピースや栞といった新しいメタファーは、ユーザーが意味を学習するまでに一定の時間を要する可能性があります。そのため、ツールチップやサイドパネル内ではアイコン単体での配置を避け、「時期の確認」「下書き」といった簡潔なラベルを必ず併記する設計が、誤解を防ぐ上で重要になると推測されます。
このように、開発者的な「正誤を判定する監視の目」を「設定の編纂をそっと見守る道具の佇まい」へと移し替えることで、高度な論理検証機能を損なうことなく、創作に向き合う心理的なハードルを緩和できる可能性が示唆されます。

User prompt: WorldCraftを初めて利用するクリエイターが、専門用語に戸惑わず自然に世界観構築を始められるオンボーディングおよびチュートリアルの体験フローを検討してください。
Response: 創作支援ツールにおけるオンボーディングでは、「最初に詳細な設定（暦の規則、世界地図、種族定義など）を入力させようとすると離脱を招く」一方で、「白紙の画面をただ渡されても何を始めればよいか途方に暮れる」という二律背反が生じやすい傾向にあります。
初見のクリエイターが専門的な知識やシステム用語を意識することなく、「書く楽しさ」と「設定がつながる便利さ（Aha Moment）」を自然に体験できる導入フローについて、各手法の利点と課題を交えながら検証します。
### 1. オンボーディング手法の比較とアプローチの選定
ユーザーを迎え入れる方式として主に3つのパターンが考えられますが、創作という主観的・偶発的な作業においては、求められる「自由度」と「誘導」のバランスが異なります。

| 方式 | 特徴 | 利点 | 潜在的な課題・検証点 |
| --- | --- | --- | --- |
| ステップ型ツアー  （ポップアップ誘導） | 「次へ」ボタンで各ペインや機能を順にハイライト解説する | 開発側の実装が比較的容易で、画面全体の構造を網羅的に見せやすい | 読まずにスキップされる確率が高く、実際の操作を伴わないため機能の価値が定着しにくい |
| 事前ヒアリング型  （ウィザード形式） | 開始前にジャンル（ファンタジー/SF等）やカレンダー形式を選択させる | ユーザーに合わせた初期設定を提供できる | 構想が固まっていない初期段階で質問攻めに遭うと、心理的負荷から離脱を招くリスク |
| インタラクティブ・サンプル型  （体験型サンドボックス） | 架空の短いエピソードが最初から開かれており、指示に沿って数行編集する | 読むだけで「何ができるか」を体感でき、専門用語を知らなくても操作結果を即座に確認可能 | サンプルの世界観がユーザーの好みに合わない場合、没入を阻害する懸念があるため、無難で普遍的なミニ設定が必要 |

この比較から、初期起動時は設定入力を一切求めず、「既存の短いエピソードを1つ触ってみる体験型ドキュメント」を用意し、その中でツールのコア価値を1〜2分で実感させるアプローチが有力と考えられます。
### 2. 初回体験の3ステップ・フロー案
ユーザーが「登録・起動」してから「自分の世界を書き始める」までの遷移を、認知負荷が急激に上がらないよう3段階に分割して検証します。
[ステップ1: 準備なしの開始] ──> [ステップ2: 1分間の体感（Aha Moment）] ──> [ステップ3: 自分の世界へ]  ・質問ウィザードなし            ・既存の文章に「@」を打ち込む             ・サンプルを閉じるか  ・普遍的なサンプルを開く        ・「3日前」が自動計算されるのを見る       ・まっさらな状態で                                  ・「食い違い」の解消を試す                  自分の作品を開始
#### ステップ1：白紙を回避するウェルカム画面
起動直後に「プロジェクト名」「暦の設定」などを入力させるモーダルは表示せず、あらかじめ用意されたサンプルノート（例：『小さな酒場の記録』など、特定の重厚な世界観に偏らない短文）が中央エディタに開かれている状態を作ります。
- 画面の佇まい:左右のサイドパネルは初期状態で折りたたまれており、中央に落ち着いたトーンのエディタだけが見えている「執筆に集中できるレイアウト」を提示します。
- 冒頭のガイド文:マニュアル的な長文ではなく、「この文章を少し書き換えるだけで、WorldCraftの仕組みがわかります」という1行の案内を本文上部に薄い文字で添える程度にとどめます。
#### ステップ2：3つのコア価値を順に触れる仕掛け
サンプルドキュメント内の指示文（下書き）に従って操作してもらうことで、これまで検討してきた「リンク補完」「相対時間」「食い違いの確認」を順に体験させます。
- インラインでの項目作成を体験する
  - 本文の指示：「ここで @ と入力して、新しい登場人物を作ってみましょう」
  - 動作：@ を打つと候補リストが現れ、適当な名前を入力してEnterを押すと、淡い点線の「下書き（仮置き）」チップが生成される。「これだけで人物が記録されます」という短いヒントを表示。
- 時間のつながりを体験する
  - 本文の指示：「『その3日後』という言葉をクリックしてみてください」
  - 動作：右サイドに小さなカードが開き、「基準の出来事から自動で計算されています」と表示される。日付を直接計算しなくても物語の時間が連動する便利さを実感させます。
- つじつま合わせ（確認）を体験する
  - 本文の指示：「この行に小さなマークが出ています。クリックして内容を見てみましょう」
  - 動作：噛み合わないパズルのアイコンをクリックすると、「登場人物がまだ生まれていない時期になっています」と表示され、「時期を直す」「理由がある」の2択を提示。怒られるのではなく「気づかせてくれる」編集アシスタントであることを伝えます。
#### ステップ3：自分の創作へのシームレスな移行
サンプルの体験が一通り完了した（または途中で「スキップして自分で書く」を選択した）段階で、次の行動へ誘導します。
- 「このサンプルを消して書き始める」ボタンいつでもサンプルを空にして自分の世界観構築を開始できる導線を常設します。
- テンプレートの任意提示（強制しない）もし最初から枠組みが欲しいユーザー向けに、「一般的な太陽暦」「シンプルな登場人物シート」といったスターターキットを、いつでもサイドバーから引き出せる形で配置しておくのが自然と考えられます。
### 3. ガイド表示におけるUI/UXの配慮
チュートリアル中の案内表示（ツールチップや吹き出し）が、実際の執筆体験を阻害しないためのルールを整理します。
- モーダルダイアログの排除:画面中央に重なって背景を暗転させるモーダルは、ユーザーの自由意志を奪い「読まされる感覚」を強めるため、画面の隅やエディタの行間に溶け込むインライン形式のカードを採用することが適していると推測されます。
- いつでも中断・再開できる構造:チュートリアルを「完了しなければ使えない必須クエスト」にせず、右上の「？」アイコンからいつでも同じサンプルを呼び出せるようにしておくことで、探究心の強いユーザーが自由に画面を触る権利を担保します。
このように、「設定作業を先に行わせる」のではなく「執筆しながら必要な機能にだけ自然に触れさせる」体験フローを構築することで、一般のクリエイターがシステム的な難解さを感じることなく、世界観構築の作業へスムーズに入り込める環境が整うと考えられます。
