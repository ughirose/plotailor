### 1. LP戦略・設計方針
#### コミュニケーションの主軸
- 「プロット専用」誤認の遮断: ファーストビューのコピーと動画／モックアップで「文章を打ち込んでいる姿（Editor）」を前面に出し、その裏でオントロジーやLint Rollerが動く様子を視覚化します。
- 作家の主権（完全ローカル）の強調: クラウドAIによる勝手な代筆や外部送信を嫌う商業作家・公募作家に対し、「通信ゼロ・推論も保存もすべて自機のPC内」という安全性を訴求します。
- 痛烈なペインの言語化: 「10万字を超えたあたりで辻褄が合わなくなる」「設定Wikiの更新に疲れて執筆が止まる」という長編特有の疲弊を突きます。

#### Section 2: Problem（課題提起）
ターゲット層であるWeb長編作家や商業クリエイターの「あるある」を言語化し、当事者意識を喚起します。
見出し: 10万字を超えたとき、物語は作家の手を離れて迷走する。
- 設定ノートの形骸化: 「NotionやWikiに緻密な設定を作ったのに、執筆が佳境に入ると更新が面倒になり、結局脳内メモリだけで書いて設定が破綻する。」
- 時系列・移動時間のバグ: 「第3章の移動時間と第12章の天候が食い違い、読者からの指摘で青ざめる。手動の見直しには膨大な精神的コストがかかる。」
- 伏線の脱落と回収漏れ: 「序盤に張ったはずの魅力的な謎やキーアイテムを、執筆の勢いの中で回収し忘れ、クライマックスの強度が落ちる。」

見出し: 設定資料を「手入れ」する時代は終わりました。

##### 補助ツール群の明記（Format / Proofread / Trace）
- Format: ワンクリックで字下げ、三点リーダー（……）偶数化、感嘆符後スペースを出版基準へ自動整形。
- Proofread: 助詞の連続、文末重複（〜だったの連続）など日本語のリズムを校正。
- Trace: 伏線フラグの足跡追跡、および視点人物の情報隔離（POVバグ）の逆引きデバッグ。

### 4. 施策の自律的検証と実務リスクの対策
- 「プロットだけ」と誤解される導線の徹底排除: ファーストビュー直下の目線が止まる位置に、あえて「エディタの全画面スクリーンショット」を配置することが有効と考えられます。「Scrivenerのように腰を据えて書ける場所である」と一目で伝われば、離脱を防ぎやすくなります。
- Lint Rollerメタファーの受容性: 「Lint」という言葉に馴染みのない一般作家層に対しては、必ず「ほころび検知」「設定の糸くず取り」という生活感のある日本語を添えて表示することが、機能の敷居を下げる必須要件となります。
- ベータ版応募のハードル: 事前のアンケート項目を増やしすぎず、「メールアドレス」と「主執筆ジャンル」の2点程度に絞り込むことで、初期のコンバージョン率（CVR）を最大化させる設計が現実的です。

#### 技術的裏付け
- ブラウザ内Gitエンジン: isomorphic-git を用いることで、Node.jsやネイティブGitをインストールすることなく、ブラウザ内のJavaScript/Wasm上でコミット、ブランチ作成、差分（Diff）計算、プッシュ/プルが完結します。
- ストレージ層: Origin Private File System (OPFS) をバックエンドに採用することで、ブラウザ標準のIndexedDBよりも高速なファイルI/Oが可能となり、大規模なリポジトリでも安定した動作が期待できます。
- データフォーマットの柔軟性: 厳密な純粋Markdownに縛られる必要はなく、本文を .md としつつ、設定や因果関係ノードを .plotailor/ontology.json や Frontmatter に分離してコミットすることで、Gitの履歴管理と相性の良いプレーンテキスト基盤を維持できます。

#### このテンプレートが機能する論理的背景
- 「Anti-Goals（非目標）」の明文化によるブレ防止: LLMは「小説執筆」と聞くと、既存の「ChatGPT的な小説自動生成」や「Notion風Wiki」「Plottr風アウトライナー」の学習データに引きずられる傾向が強くあります。「これはやらない（Anti-Goals）」を明確に箇条書きで縛ることで、議論が既存ツールの焼き直しに退行するのを防ぎやすくなります。
- 「Editor」と「Lint Roller」の力関係の固定: Plot（構成）という名前に引きずられてエディタ機能が軽視されるのを防ぐため、Editorを【主役】、Lint Rollerを【差別化コア】と明記し、両者の役割分担を揺るがさない構造にしています。
- 技術制約（OPFS / isomorphic-git / Zero Cloud）の事前インジェクション: アーキテクチャの前提を渡しておくことで、「自社クラウドデータベースにユーザーの原稿を保存して…」といった、本プロダクトの思想（ローカルファースト・自社インフラコスト極小化）に反する無駄なアーキテクチャ提案を初手で排除できます。
