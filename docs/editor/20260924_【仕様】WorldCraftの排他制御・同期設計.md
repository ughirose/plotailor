Response: 物語論（ナラトロジー）における「事件が起きた客観的順序（ファブラ / ヴェルク）」と「物語として読者に語られるテキスト上の順序（シュジェ / ディスコース）」は、ミステリの倒叙や回想（アナルプシス）、未来予知（プロレプシス）を多用する長編作品において必然的にねじれの位置関係となります。
この構造的乖離を単一の軸に押し込めるのではなく、「客観的時空軸（Story Time）」と「読者体験軸（Discourse Time）」という直交し得る2軸としてUI上で対比・連動させるための設計モデルを検証します。
#### 1. 2つの時間軸の数理的定義と関係性
2つの時間軸は、数学的な性質において根本的に異なると考えられます。
- 客観的時間軸（Story Time / Fabula）: 作中の通算絶対日（Absolute Narrative Day tstory​∈R）に基づく物理的・絶対的な時間です。Layer 0 の TrFN ファジー時間や世界観の歴史年表がここに位置づけられ、因果律（原因は常に結果に先行する）が単調増加として成立します。
- 読者体験軸（Discourse Time / Sjuzhet）: 本文テキストの進行順序（章番号、シーン境界インデックス、または累計文字数 tdiscourse​∈N）に基づく順序です。読者がページをめくる体験に沿って常に 1,2,3,…,N と単調増加します。
【時系列のねじれ（回想と倒叙）の構造】  Discourse Time (読者の読書順) ──>  [Scene 1: 現代の事件] ──> [Scene 2: 10年前の回想] ──> [Scene 3: 現代の解決]          │                          │                          │          │ (写像)                   │ (逆行)                   │ (順行)          ▼                          ▼                          ▼  [Day 3650: 殺人事件]       [Day 0: 過去の契機]        [Day 3651: 真相解明]  Story Time (客観的通算絶対日) ──>
テキスト順から客観時間への写像 f:tdiscourse​↦tstory​ をプロットした際、単調増加関数であれば完全な「時系列順の語り」となりますが、傾きが負になる区間は「回想（Flashback）」、前方にジャンプする区間は「未来跳躍（Flashforward）」として視覚的に同定されます。
#### 2. デュアル軸UIのレイアウト・トポロジー比較
両軸をどのように画面内に配置し、対比させるかについては、主に3つの設計アプローチが考えられます。

| 評価軸 | パターンA: 軸切り替えトグル型 | パターンB: 上下並列リボン型 (Parallel Ribbons) | パターンC: 2次元直交プロット (Narrative Mapping Plot) |
| --- | --- | --- | --- |
| 画面占有率 | 極小（既存のタイムラインバー1本で共用） | 中（エディタ下部に2本のトラックを配置） | 大（独立したフルサイズパネルが必要） |
| 時系列のねじれの可視性 | 低い（切り替え時に要素が並び替わるのみで対応線が見えない） | 高い（2軸間の対応関係がリボン状の接続線で一目瞭然） | 最高（回想の深さや時間密度が2Dグラフの傾きとして完全可視化） |
| スクラブ操作性 | 良好（単一のバーを操作） | 極めて良好（どちらの軸をスクラブしているか明確） | 中（2D空間上のカーソル選択となり直感的操作がやや難） |
| 適したフェーズ | 集中執筆時（Prose Focus） | 日常的な推敲・伏線確認（標準モード） | 大規模なプロット構成・構成リファクタリング時 |

##### 推奨されるハイブリッド・ビューポート
日常的な執筆・推敲のコンテキストにおいては、画面占有率と視認性のバランスに優れる「パターンB（上下並列リボン型）」を下部トレイの標準とし、作品全体の構造再編を行う際に「パターンC（2次元プロット）」へフルスクリーン展開できるオプトイン構成が実用的と推測されます。
#### 3. 上下並列リボン型（Parallel Ribbons）の描画・同期仕様

##### A. 視覚要素と接続幾何学（Connecting Splines）
- 上段（Discourse Track）: シーンブロックが「原稿の文字数」または「シーンの並び順」に比例した幅で均等に並びます。読者が体験するテンポ感を反映します。
- 下段（Story Track）: 作中の通算絶対日（Narrative Day）の実時間スケールで配置されます。数日間の出来事は狭い領域に密集し、数年間の空白（時間省略 / Ellipsis）は広い隙間として描画されます。
- 2軸間の接続スプライン（Connection Splines）: 上下の対応するシーン同士を半透明のベジェ曲線で結びます。
  - 順行（直線・右下がり）: 通常の時系列通りの語り。
  - 回想（左下がり・クロス）: スプラインが逆方向へ交差し、視覚的に「過去へのジャンプ」を警告。交差線には青色のアクセントを付与。
  - 未来描写（急な右下がり）: 「未来の光景」が先出しされている区間。紫色のアクセントを付与。
##### B. 双方向スクラブと同期フィードバック
どちらの軸のインジケータをドラッグ（スクラブ）するかによって、システムの挙動を非対称に設計する必要があります。
- Discourse 軸を操作した場合（読書シミュレーション）:
  - 上段のカーソルを動かすと、CodeMirror 6 の本文エディタが該当シーンへ即座にスクロール。
  - 下段の客観時間軸上では、現在読んでいるシーンの発生日時へインジケータが「跳躍（ワープ）」し、相関図キャンバスがその日時の主観認識状態へモーフィング。
- Story 軸を操作した場合（歴史探索シミュレーション）:
  - 下段の歴史時間を連続的に動かすと、相関図や世界地図が客観的な歴史順で滑らかにアニメーション変化。
  - 上段の Discourse 軸上では、「その歴史的出来事が本文のどこで描かれているか（あるいは未描写か）」がハイライト。複数箇所で言及されている場合（例: 伏線配置と真相告白）は、上段の複数シーンが同時に淡く点灯。
#### 4. 技術的裏付けとビジネス価値（ROI）の検証
##### 技術的裏付け（Technical Feasibility）
- 非同期射影インデックス: シーン境界メタデータ（scene_id, offset, time_range）から、双方向の参照テーブル（DiscourseToStoryMap および StoryToDiscourseIntervalTree）を Web Worker 内で構築。O(logN) での双方向参照が可能なため、スクラブ操作時にも60fpsの描画追従を担保しやすいと考えられます。
- Canvas/SVG 負荷分散: リボン状のブロック要素は HTML/CSS、交差する接続スプライン群は単一の透明 <svg> レイヤーで一括描画し、非表示領域（画面外にスクロールアウトしたシーン）のパス計算をクリッピングすることで、数百シーン規模の長編でもメモリフットプリントを最小限に維持可能と推測されます。
##### ビジネス価値と作家の投資対効果（ROI）

| 創作プロセスにおける課題 | 従来の執筆環境（Scrivener/紙等） | WorldCraft デュアル軸タイムライン | 投資対効果（ROI）の評価 |
| --- | --- | --- | --- |
| 回想・時系列の矛盾 | 「10年前の回想で登場したアイテムが、実は作中設定では5年前に発明されたものだった」といった設定破綻が後から発覚。 | 客観時間軸側でアイテムの存在期間（Valid Time）とシーンの対応が自動照合され、即座に不整合ラインを検出。 | 大規模改稿・リライト工数の根本的排除（推定数十時間のロス削減）。 |
| 読者の情報開示ペース管理 | 「客観的にいつ起きたか」と「読者がいつ知るか」の距離感が掴めず、種明かしが早すぎる・遅すぎるといった構成不良が発生。 | 接続線の傾きや密度を見るだけで、謎の配置から回収までの「読書体験上のインターバル」を定量的に可視化。 | 物語のサスペンス・牽引力（リーダビリティ）を狙い通りに精密チューニング可能。 |

#### 5. 潜在的リスクと自律的な検証
このデュアル軸モデルを運用するにあたり、以下の文芸特有のエッジケースに対する許容度を設けておく必要があります。
- 時間の特定不能なシーン（Floating Scenes）: 詩的なモノローグ、抽象的な精神世界、神話的なプロローグなど、作中の絶対通算日（tstory​）を特定できない（あるいは意図的に定義しない）シーンが存在します。
  - 対策案: tstory​=null（あるいは UNDETERMINED）の許容。これらは客観時間軸上では「時空未定義トレイ（Unanchored Dock）」に退避させ、Discourse 軸上でのみ通常通り配置するフォールバック設計が妥当と考えられます。
- 時間の伸縮（Pacing Distortion）の過剰視覚化: 緊迫した10秒間の戦闘を3章（1万字）かけて描写するケースや、100年の平和を1行で飛ばすケースにおいて、両軸のスケール差が極端に開き、接続スプラインが画面を埋め尽くすリスクがあります。
  - 対策案: Story 軸のスケール表示において、空虚な時間間隔を対数スケール（Logarithmic Scale）または「非線形アコーディオン圧縮」で折りたたむスライダービューの導入が有効と推測されます。
このように、読者の受容プロセスと作品世界の客観史を分離しながら相互の射影関係を提示するデュアル軸アプローチは、複雑な構成を持つ長編文芸の構築において極めて強固な論理的支柱となり得ると考えられます。

Response: 伏線（Foreshadowing）の配置（Plant）と回収（Payoff）は、物理的な因果関係（Layer 1 DAG）に基づきながらも、本質的には「読者の期待管理と情報開示のコントロール（Discourse Time上の演出）」という側面を強く持ちます。

#### 1. 伏線アークの幾何学的射影とトポロジー
伏線リンクをどの軸に描画するかによって、作家が知覚できる情報の本質が異なります。
【Discourse Track（読者体験軸）上のアーク】         ┌─────────────────── 伏線アーク (Arc) ───────────────────┐         │                                                        ▼  [Scene 02: 鍵の発見] ─── [Scene 05: 会話] ─── [Scene 12: 秘密の扉] ─── [Scene 18]  (Plant: plant_key)                            (Payoff: payoff_key)  ※「読者が謎を抱えたまま読み進めるテキスト量（文字数・テンポ）」を表現                     ↕ 軸の役割の違い【Story Track（客観時間軸）上のアーク】  [Day 100: 鍵の製造] ─────────────────────────> [Day 365: 扉の解錠]  ※「物理世界でアイテムや因果が存続していた実時間」を表現
##### 描画対象軸の比較検証
- Discourse Track（読者体験軸）への描画（推奨）: 読者が「伏線を意識してから解決されるまでの読書体験上の距離感（Pacing）」を直接反映できるため、文芸的なカタルシスやサスペンスの持続時間を直感的に把握しやすい利点があります。
- Story Track（客観時間軸）への描画: 回想や時間跳躍が挟まると、読者にとってはすぐ次のシーンであっても時間軸上では何年も離れるため、アークが極端に間延びし、読書テンポの評価には不向きとなる傾向があります。
したがって、「伏線アークは Discourse Track（読者体験軸）の上部にアーチ状に架橋し、必要に応じて Story Track 側の対応スプラインと連動させる」アプローチが最も自然な視覚化になると推測されます。
##### パラボラ・ベジェ曲線の動的幾何計算
複数のアークが重なり合って画面を覆い尽くす（Visual Clutter）のを防ぐため、スパン（始点と終点の距離）に応じた動的スケーリングが必要です。
- 高さの非線形スケーリング: 始点座標 x1​、終点座標 x2​、距離 L=∣x2​−x1​∣ としたとき、アーク頂点の高さ H(L) を単純な線形（H∝L）にすると長距離アークが画面外へ突き抜けます。H(L)=Hmin​+(Hmax​−Hmin​)⋅(1−e−L/σ)このような飽和型関数（あるいは対数スケール）を用いることで、短スパンの伏線は低くコンパクトに、長編全体にまたがる大伏線は高く滑らかな弧を描きながら一定の表示領域内に収めることが可能と考えられます。
- 制御点オフセットによる交差回避: 三次ベジェ曲線（Cubic Bézier）の制御点 (Cx1​,Cy1​),(Cx2​,Cy2​) において、同一シーンから複数の Plant が発生している場合は、制御点のX軸オフセットを微小に散乱（Jittering）させ、線の重なりを抑制します。
#### 2. 伏線ライフサイクルと回収漏れの数理的判定ロジック
単に「まだ回収されていない」というだけでは、現在執筆進行中である通常の未回収状態と、プロット上の「回収漏れ（事故）」を区別できません。システムが警告を発すべき状態を定義するため、以下の4値ライフサイクル状態遷移モデルが検討されます。
                    ┌─────────────────────────┐                    │  UNRESOLVED (未回収)    │                    └────────────┬────────────┘                                 │         ┌───────────────────────┼───────────────────────┐         ▼                       ▼                       ▼┌─────────────────┐     ┌─────────────────┐     ┌─────────────────┐│ RESOLVED (解決) │     │ DANGLING (漏れ) │     │ ABANDONED (放棄)││ Payoff 到達     │     │ デッドライン超過│     │ 意図的ミスリード│└─────────────────┘     └─────────────────┘     └─────────────────┘

| 状態名 | 判定条件（述語論理） | UI上の視覚表現 | システムの挙動 |
| --- | --- | --- | --- |
| UNRESOLVED | ∃Plant(p)∧¬∃Payoff(p)∧Cursor≤Deadline(p) | 青色・細い実線アーク（終端は浮遊矢印） | 執筆中の正常な伏線。警告は出さず、現在地からの距離のみを表示。 |
| RESOLVED | ∃Plant(p)∧∃Payoff(p)∧Offset(Plant)<Offset(Payoff) | 緑色・落ち着いた実線アーク | 正常回収。ホバー時にカタルシススコアや解決シーンをプレビュー。 |
| DANGLING | ∃Plant(p)∧¬∃Payoff(p)∧ExceedsDeadline(p) | 赤色・点滅する破線アーク（終端に警告マーク） | 回収漏れ警告。エディタのガターおよび監査パネルに要対応通知を発火。 |
| ABANDONED | ユーザーによる明示的な「未回収（ミスリード・打ち切り）」フラグ付与 | 灰色・減衰ドット線 | 意図的な不条理劇や未解決ミステリとして扱い、警告対象から除外。 |

##### 「回収漏れ（DANGLING）」を検知する境界条件
以下のいずれかの条件を満たした瞬間に、システムは UNRESOLVED から DANGLING への状態遷移を評価します。
- 章・部（Volume）の境界超過: 伏線ノードにスコープ（例: scope: "chap_03" や scope: "vol_01"）が指定されており、原稿の執筆位置がその章や部を通過して完了ステータスになった場合。
- キーエンティティの物理的消失（Layer 0/1 連動）: 伏線の担い手であるアイテムが破壊された、あるいは関連キャラクターが死亡・退場し、物語の構造上 Payoff を発生させることが不可能になった場合。
- 作品完結フラグの点灯: エピローグが執筆された、または全体エクスポートを実行しようとした時点で、1つでも未回収リンクが存在する場合。

##### A. 開放端アーク（Open-ended Arc）の表現
未回収の伏線（UNRESOLVED および DANGLING）は終点ノードが存在しないため、アークの着地先を工夫する必要があります。
- 現在執筆地点（Cursor Position）への動的ランディング: 弧の終点を「現在エディタで執筆している最新シーン」へと暫定的に接続します。執筆が進むにつれてアークが右へ引き伸ばされ、作者に対して「この謎を未解決のまま何文字引っ張っているか」を視覚的に意識させる効果が期待されます。
- 目標ピン（Target Marker）への接続: プロット段階で「第5章で回収予定」とアノテーションされている場合は、第5章のブロック上空に半透明のゴーストアンカーを表示し、そこへ破線を落とします。

#### 6. 自律的な設計判断とトレードオフの検証
この監査エンジンを組み込む上で、文芸創作の特異性に対する以下の配慮が重要になると推察されます。

- 叙述トリック（Narrative Trick）の保護: 作者が読者を意図的に騙すために、あえて偽の因果関係を信じ込ませるケース（ミステリの骨子）が存在します。

単一のグラフで両者を無理に混在させると、システムがプロットの意図的な欺瞞を「論理矛盾」として誤検知するか、逆に重大な破綻を見落とす危険性が生じます。この課題を克服するための二重DAG（Dual-DAG）モデルの数理構造、写像メカニズム、監査ロジック、およびUI設計について検証します。
#### 1. 二重DAGアーキテクチャの基本構造と写像関係
二重DAGは、互いに独立した2つのグラフが存在するのではなく、「真の客観DAG」を基底とし、テキスト上の記述や伏線（Discourse）を通じて「読者の認識空間へ投影された射影グラフ」として定義することが合理的と推測されます。
【基底層: 客観DAG (G_true)】 ── 作中世界の物理的・客観的真実  [Node A: 1990年の殺人] ────── (時間差: 30年) ──────> [Node B: 2020年の捜査]  (犯人: char_X, 年齢: 20)                              (同一人物: char_X, 年齢: 50)                     │                     ▼ 【叙述フィルター (Narrative Projection Filter)】                     │   ・人物エイリアス (名前の意図的混同)                     │   ・時間軸の並置 (カットバックによる錯覚)                     │   ・偽エッジの注入 (語り手の信頼できない言明)                     │【射影層: 見かけのDAG (G_apparent)】 ── 読者（または探偵）が認識している世界  [Node A': 現代の事件1] ─── (同時代・連続) ───> [Node B': 現代の事件2]  (容疑者: char_Y)                               (捜査官: char_X)
##### 2つのグラフの形式的定義
- 客観DAG (Gtrue​=(Vtrue​,Etrue​)): Layer 0（物理時空）および Layer 1（因果関係）の厳密な制約に従う有向非巡回グラフ。すべてのノードは確定した作中通算絶対日（tstory​）を持ち、物理法則や存在論的矛盾を一切内包しない正史。
- 見かけのDAG (Gapparent​=(Vapp​,Eapp​)): 読者が本文テキストを読み進める過程（Discourse Time）で順次構築される心内表現モデル。客観DAGのノードやエッジに対し、隠蔽・結合・分裂・偽装の変換が施された派生グラフ。
#### 2. 代表的な叙述トリックのグラフ操作（Graph Mutation）

- 自然言語からの一階述語論理化の限界: 「なんとなく怪しい素振り」「物悲しげな目つき」といった心理的・情緒的手がかりを論理式に変換することは不可能です。 したがって、このアルゴリズムが検証する対象は「アリバイ、物理的アクセス権、凶器の適合性、科学的痕跡」といった硬質な物理的・客観的ファクトに限定し、心理的手がかりは注釈メモとして扱う境界線が妥当と考えられます。
- アブダクション（仮説形成）との住み分け: 現実の推理小説の多くは、純粋な数学的演繹（Deduction）だけでなく、「状況証拠から最も確からしい仮説を導く最良の説明への推論（Abduction）」に依存しています。 対立仮説を数学的に100%消去できない場合であっても、確率論的・優先度付き制約（Soft Constraints / MaxSMT）を取り入れ、「対立仮説Cは成立するが、極めて不自然な仮定を3つ必要とする」といった蓋然性のグラデーションとして作者に提示するアプローチが、文芸ツールとしてより調和的であると推察されます。

User prompt: 純粋演繹では消去しきれない状況証拠を、Soft Constraints（MaxSMTやベイズ的確からしさ）を用いて評価し、推理の説得力をスコアリングする数理モデルの設計について教えてください。
Response: ミステリや文学的プロットにおける「状況証拠からの推理」は、数学的な完全演繹（すべての別解の完全消去）だけで成立することは稀であり、多くは「最も不自然な仮定が少なく、証拠を包括的に説明できる仮説」を選択する最良の説明への推論（Inference to the Best Explanation / Abduction）に依存しています。
この曖昧さを伴う文芸的説得力を定量化・監査するため、物理的真偽を判定する「ハード制約（Hard Constraints）」と、蓋然性や不自然さを評価する「重み付きソフト制約（Weighted Soft Constraints / MaxSMT）」、さらに「ベイズ的証拠更新」を融合させた数理モデルの妥当性を検証します。
#### 1. 演繹からアブダクションへの拡張：ハイブリッド数理フレームワーク

#### 2. MaxSMT とオッカムの剃刀によるペナルティ設計
MaxSMT（Maximum Satisfiability Modulo Theories）の枠組みを用い、各仮説 h∈Hsurvived​ に対して「成立のために要求される不自然な前提」にペナルティコストを課す目的関数を定式化します。
##### コスト関数の定義
仮説 h が成り立つために追加で要求される「未証明の仮定・偶然・作為の集合」を A(h)={a1​,a2​,…,am​} とし、各要素に重み w(ai​)∈R+ を割り当てます。
Cost(h)=ai​∈A(h)∑​w(ai​)+cj​∈Cunexplained​(h)∑​λj​
ここで、Cunexplained​(h) は「仮説 h を採用しても説明がつかずに残ってしまう不審な証拠（余剰証拠）」の集合であり、λj​ はその放置ペナルティです。
##### ペナルティ重み（コスト）の配分仕様案

| 不自然さの類型 | 形式的定義 / 違反の具体例 | ペナルティ重み w | 文芸的妥当性の背景 |
| --- | --- | --- | --- |
| 奇跡・天文学的偶然  (Coincidence) | 独立した事象の同時発生  （例:「犯行時刻に偶然落雷で停電した」） | 極大 (w≈50) | 偶然への依存度が高い推理は、読者に「ご都合主義」と受け取られやすいため。 |
| 超人的・極端な身体能力  (Physical Anomaly) | 人間の通常スペックを逸脱した行動  （例:「高さ4mの塀を道具なしで跳躍」） | 大 (w≈30) | 特別な設定（特殊能力等）が公理にない限り、大きな違和感を生む要因。 |

ソルバーは Cost(h) を最小化する仮説（最小のコストで全証拠を回収できる仮説）を探索します。
#### 3. ベイズ的確からしさ（Bayesian Plausibility）モデル
MaxSMTが離散的なペナルティ計算に適しているのに対し、複数の状況証拠が累積して犯人を指し示す「証拠の補強効果」をモデル化するには、オッズ形式のベイズ更新が適していると考えられます。
##### 事後オッズ比による対立仮説の比較
真相仮説 htrue​ と対立仮説 halt​（例: 「別の容疑者による犯行説」）の相対的な説得力は、証拠集合 E={e1​,e2​,…,en​} が与えられた際の事後オッズ比（Posterior Odds）として評価できます。
P(halt​∣E)P(htrue​∣E)​=P(halt​)P(htrue​)​×k=1∏n​P(ek​∣halt​,E<k​)P(ek​∣htrue​,E<k​)​
- 事前確率比 P(halt​)P(htrue​)​: 動機の強さ、犯行機会（機会格差）に基づくベースラインの確からしさ。
- ベイズファクター（尤度比） P(ek​∣halt​)P(ek​∣htrue​)​: 各証拠 ek​（例:「現場に残された靴の泥」）が、どちらの仮説のもとで自然に生じるかを表す指標。
##### 総合説得力スコア（Plausibility Score）の統合式
MaxSMTのコスト関数とベイズ確率を統合し、作者に提示する直感的なスコア S(h)∈[0,100] を以下のように導出することが考えられます。
S(h)=100×相対的確からしさ (Probability)∑h′∈H​P(h′∣E)P(h∣E)​​​×オッカムの剃刀減衰 (Parsimony)exp(−κCost(h)​)​​
（ここで κ は作品ジャンルに応じた寛容度スケーリング係数）

#### 4. 縦書き（vertical-rl）および横書き環境における幾何学的配慮
書字方向の切り替え（Writing-Mode Agnostic）に対応するにあたり、CM6のDOM構造とツールチップの座標計算において以下の技術的調停が必要となります。
- ホバーツールチップの座標変換（Coordinate Mapping）: 横書きでは top / bottom 方向に展開するポップオーバーですが、縦書き（vertical-rl）では行送り方向が「右から左（X軸マイナス方向）」となります。 CM6標準の tooltips() 拡張をそのまま使うと、ツールチップが縦書きテキストの上に被さって文字を隠してしまうため、コンテナの writingMode を判定し、縦書き時は「対象行の左側（進行方向の余白）」または「下側（地側）」へ動的にオフセットを再計算する幾何補正レイヤーを導入します。
- インラインチップの幾何シフトの抑制: 縦書き環境で block: true のWidgetを挿入すると、テキスト全体が左方向へ激しくシフトします。執筆中の画面の揺れを防ぐため、解決編サマリーチップは本文ブロック内へ埋め込むのではなく、行の上端（天側のマージン領域）に絶対配置（position: absolute）するオーバーレイ方式を採用するのが妥当と考えられます。

#### 6. 自律的な設計判断とトレードオフの検証

- 「警告過多による認知疲労（Alert Fatigue）」の回避: 推論スコアが常にピコピコと変動したり、文章を書くたびに波線が増減すると、作家の集中力が削がれる恐れがあります。 そのため、通常執筆時は「ガターに極小のカラーインジケータ（緑/黄/赤のドット）を灯すのみ」とし、スコアの詳細や反例リストは作者が意識的にサイドバーを開いたとき、あるいは解決編の節目に到達したときにのみ確認できる「段階的開示（Progressive Disclosure）」の節度を保つことが、文芸IDEとしての品位を維持する着地点と考えられます。

#### 1. シリアライズ方式の比較とアーキテクチャ選定
ブラウザのメインスレッドと Web Worker 間の通信において検討される代表的なフォーマットについて、レイテンシ、GC（ガベージコレクション）負荷、実装複雑性の観点から比較します。

| 評価軸 | パターンA: 構造化複製 / JSON (Structured Clone) | パターンB: 完全ゼロコピー (SharedArrayBuffer) | パターンC: ハイブリッド・バイナリ (Transferable ArrayBuffer + FlatBuffers) |
| --- | --- | --- | --- |
| シリアライズ／パース速度 | 中〜低（数千ノードで数ミリ秒〜十数ミリ秒のオーバーヘッド） | 最速（0ms・メモリ共有） | 極めて高速（サブミリ秒・ゼロコピー転送） |
| メインスレッドのGCプレッシャー | 高（キーストロークごとに一時オブジェクトが大量生成されGCスパイクを誘発） | ゼロ | 極小（バッファの再利用が可能） |
| セキュリティ制約・可搬性 | 制約なし（通常のWeb環境で即座に動作） | 厳格（COOP/COEP ヘッダー必須、配布形態に制約） | 制約なし（標準の Transferable Objects を利用可能） |
| データ構造の柔軟性 | 極めて高い（ネストしたオブジェクトをそのまま送受信） | 低（固定長メモリ領域の手動管理、アトミック同期が必須） | 高（スキーマ駆動でバイナリと構造化データを両立） |
| 実装・保守コスト | 極小 | 極大 | 中程度 |

##### 選定の検証：ハイブリッド・バイナリ方式の妥当性
- 純粋JSONの限界: 本文編集に伴い250msごとに発火するリアルタイム監査において、数百件の手がかりや仮説式を JSON.stringify / parse すると、メインスレッドで周期的なマイクロフリーズが生じるリスクがあります。
- SharedArrayBuffer の配布リスク: PWAやローカルHTML配信において Cross-Origin-Opener-Policy (COOP) や Cross-Origin-Embedder-Policy (COEP) の要求は、外部フォント読み込みやiframe連携での制約となりやすい傾向があります。
- 推奨アプローチ: 数値インデックスや制約フラグなどの高頻度・固定長データは Transferable ArrayBuffer（所有権移転によるゼロコピー） でWorkerへ渡し、人間可読なエラーメッセージや未構造化メタデータのみを軽量な辞書テーブルとして後置する「FlatBuffersライクなハイブリッド・バイナリレイアウト」が、速度と可搬性のバランスにおいて優れていると推測されます。
#### 2. リクエスト仕様（CodeMirror 6 → Z3 WASM Worker）
エディタ側で構文解析された差分トークンを、Worker内のZ3コンテキストへ注入するためのシリアライズフォーマットです。

- generation: ドキュメントの変更世代番号（最新世代以外の破棄判定用、uint32）
- scene_index: 解決編または現在カーソルが存在するシーン番号（uint32）
- timeout_ms: ソルバーの最大許容計算時間（例: 50 ms、uint32）

| --- | --- | --- | --- |

| to_pos | uint32 | 4B | CodeMirror 6 ドキュメント内の終了オフセット。 |

| constraint_op | uint16 | 2B | 演算子（EQ, NEQ, GT, LT, IMPLIES, NOT）。 |

#### 3. レスポンス仕様（Z3 WASM Worker → CodeMirror 6 / Sidebar）
Workerが求解（Solve / Optimize）を完了した際、エディタのデコレーション更新用データと、サイドバーUIのViewModel用データを構造化して返却します。
【AuditResponse ペイロード構造】┌──────────────────┬──────────────────┬──────────────────┬──────────────────┐│  Request ID (4B) │ Generation (4B)  │ Status Code (2B) │ Global Score (2B)│  <-- Header (12B)├──────────────────┼──────────────────┴──────────────────┴──────────────────┤│  Summary Float   │ Parsimony: f32 │ Coverage: f32  │ Motive: f32          │  <-- 診断指標 (12B)├──────────────────┼────────────────────────────────────────────────────────┤│  Decorations     │ [Range 1: from, to, type, score] [Range 2: ...]        │  <-- CM6 反映配列├──────────────────┼────────────────────────────────────────────────────────┤│  Hypothesis List │ [Rank, Cost, Status, Model-ID, Name-Offset] ...        │  <-- ランキング├──────────────────┼────────────────────────────────────────────────────────┤│  MUC Array       │ [Unsat Core Token IDs: uint32[]]                       │  <-- 最小反例ID列└──────────────────┴────────────────────────────────────────────────────────┘
##### A. 診断指標とステータス
- status_code:
  - 0x00: OPTIMAL（正常求解完了、パレート最適解を導出）
  - 0x01: SAT_UNDERDETERMINED（充足可能だが別解が複数存在）
  - 0x02: UNSAT_OVERCONSTRAINED（ハード制約同士が矛盾・プロット破綻）
  - 0x03: TIMEOUT（有界時間内に探索未完了、暫定最良解を返却）
- global_score: 0∼100 の総合説得力スコア（uint16）。
##### B. デコレーション命令列（DecorationCommand: 固定長 16 bytes）
CodeMirror 6 の EditorView に直接マッピング可能な差分命令です。
#[repr(C)]struct DecorationCommand {    from: u32,             // 本文適用開始オフセット    to: u32,               // 本文適用終了オフセット    decoration_type: u16,  // 0: NONE, 1: BLUE_SOLID, 2: YELLOW_WAVY, 3: RED_DOT    severity: u16,         // 警告レベル (INFO, WARNING, HARD_ERROR)    assoc_hypothesis: u32, // 関連する対立仮説ID（String Pool参照）}
CM6側はこのバッファを受け取った際、オブジェクト変換を介さずに Float64Array または Uint32Array のビューを通じて直接 RangeSetBuilder に流し込めるため、メインスレッドでのアロケーションが最小化されます。
##### C. 最小反例集合（MUC: Minimal Unsatisfiable Core）
真相仮説が棄却された場合、または対立仮説が生き残った場合に、「どの手がかりが原因で衝突しているか」を示す token_id の配列です。UIはこのIDを逆引きして、エディタ上の該当行をフォーカス・強調します。
#### 4. Z3 WASM 内部におけるインクリメンタル処理
シリアライズされたパケットを受け取った Worker 側でのメモリ操作と、計算量を抑えるための状態保持の挙動です。
[Incoming CluePacket (ArrayBuffer)]                │                ▼┌────────────────────────────────────────────────────────┐│ Z3 Context Manager (Rust / C++ WASM)                   ││                                                        ││  [Axiom Base Frame] (作品世界の普遍物理公理)           ││  ────────────────────────────────────────────          ││   solver.push() // チェックポイント                    ││     ├─ 固定長レコード配列を走査し、ASTノードを生成     ││     ├─ soft_weight > 0 の制約を Optimize に登録        ││     ├─ solver.check() / solver.optimize()              ││     └─ モデル抽出およびコスト評価                      ││   solver.pop()  // フレーム破棄 (メモリ解放)           │└────────────────────────────────────────────────────────┘
- 文字列パースの完全排除: テキスト形式の SMT-LIB2（z3::Context::parse_string）は使用せず、C/Rust APIの Z3_mk_eq、Z3_mk_implies などのネイティブ関数ポインタを直接呼び出してASTを構築します。これにより、WASM内部での文字列パースコストを回避します。
- スコープスタックの活用（push / pop）: 作品の基本設定（登場人物の初期パラメータや地理関係）を基底フレーム（Depth 0）に保持したまま、シーンごとの一時的な手がかりを push() されたフレーム（Depth 1）で解き、処理完了後に pop() することで、Solverインスタンスの再生成オーバーヘッドを排除します。

#### 6. 自律的な設計判断とフォールバック境界

##### StateField 保持と ViewPlugin 保持の比較検証

| 評価軸 | パターンA: StateField で保持（推奨） | パターンB: ViewPlugin で保持 |
| --- | --- | --- |
| 打鍵時の追従性 | 完全自動。  decorations.map(tr.changes) により、Worker推論中も警告位置が文字入力に追従。 | 手動計算が必要。  update(viewUpdate) 内で差分マッピングを自前実装する必要があり、破綻リスクあり。 |
| Undo/Redo 耐性 | 極めて高い。  エディタの履歴スタックと整合性を維持しやすい。 | 低い。  履歴巻き戻し時に装飾位置の不整合（ゴースト下線）が発生しやすい。 |
| メインスレッド負荷 | Worker結果受信時と打鍵時のマッピング処理で微小な計算が発生。 | Viewの更新時のみ描画するため初期描画は軽いが、状態管理が複雑化。 |

Workerからの推論結果が届くまでの「遅延時間（250〜500ms）」の間にもユーザーはタイピングを継続しているため、StateField を用いてトランザクションの changes に対しデコレーション位置を自動マッピング（RangeSet.map）させるアプローチが、文芸エディタとしての体験品質を保つ上で不可欠と考えられます。
#### 2. バイナリデコーダと RangeSetBuilder の最適化設計
CM6の RangeSetBuilder は、登録する範囲（from）が狭義の単調増加（昇順）でなければ例外（Error: Ranges must be added in sorted order）をスローするという厳しい仕様を持ちます。
##### メインスレッドでのソート処理を回避する設計
メインスレッドで Array.prototype.sort() を実行すると、O(NlogN) の計算量と一時オブジェクト生成によってフレーム落ちを誘発するリスクがあります。 したがって、「Z3 WASM Worker側が、出力バッファへ書き込む時点で from 昇順にソートして格納することをプロトコル上の不変条件（Invariant）とする」設計が妥当と考えられます。
【Worker側でのソート済みバイナリ出力】  Offset: 0B         16B        32B        48B         [Token A]  [Token B]  [Token C]  [Token D]  From:   102        240        240        512  To:     115        250        260        530  ※同一 from の場合は to の昇順で格納
##### ドキュメント境界超過（Out-of-bounds）へのフェイルセーフ
非同期推論中にユーザーが大量のテキストを一括削除した場合、Workerから届いた to 座標が現在の state.doc.length を超過する可能性があります。 デコードループ内で以下のクランプ処理を適用し、エディタクラッシュを未然に防ぎます。
safeFrom=min(from,docLength),safeTo=min(max(to,safeFrom),docLength)

##### B. StateField による高速デコードと差分更新
バイナリバッファ（DataView または Uint32Array）を直接イテレーションし、オブジェクトを介さず DecorationSet を構築します。
const AUDIT_HEADER_SIZE = 48; // 前回のパケット仕様に準拠const COMMAND_RECORD_SIZE = 16;export const auditDecorationField = StateField.define<DecorationSet>({  create() {    return Decoration.none;  },  update(decorations, tr) {    // 1. 打鍵や編集がある場合、既存のデコレーション位置を自動追従    let mappedDecorations = decorations.map(tr.changes);    // 2. Workerから新しい推論結果パケットが届いた場合の更新    for (const effect of tr.effects) {      if (effect.is(setAuditDecorationsEffect)) {        const buffer = effect.value;        const view = new DataView(buffer);        const docLength = tr.newDoc.length;        // ヘッダー解析        const magic = view.getUint32(0, true);        if (magic !== 0x57434c55) {          console.warn("[WorldCraft] Invalid audit binary magic");          return mappedDecorations;        }        const recordCount = (buffer.byteLength - AUDIT_HEADER_SIZE) / COMMAND_RECORD_SIZE;        const builder = new RangeSetBuilder<Decoration>();        let lastFrom = -1;        let lastTo = -1;        for (let i = 0; i < recordCount; i++) {          const offset = AUDIT_HEADER_SIZE + i * COMMAND_RECORD_SIZE;          const rawFrom = view.getUint32(offset, true);          const rawTo = view.getUint32(offset + 4, true);          const decType = view.getUint16(offset + 8, true);          // severity, assocHypothesis 等はホバー用マップまたは別途保持          // 安全境界クランプ          const from = Math.min(rawFrom, docLength);          const to = Math.min(Math.max(rawTo, from), docLength);          if (from === to) continue; // 長さ0の範囲はスキップ          // 昇順制約の遵守チェック（Worker側のソート不整合に対する防御）          if (from < lastFrom || (from === lastFrom && to < lastTo)) {            continue; // 不正順序レコードの無視          }          const mark = decType === 2             ? DECORATION_STYLES.YELLOW_WAVY             : decType === 3               ? DECORATION_STYLES.RED_DOT               : DECORATION_STYLES.BLUE_SOLID;          builder.add(from, to, mark);          lastFrom = from;          lastTo = to;        }        return builder.finish();      }    }    return mappedDecorations;  },  provide: (field) => EditorView.decorations.from(field)});

import { ViewPlugin, ViewUpdate } from "@codemirror/view";export const auditTooltipPlugin = ViewPlugin.fromClass(  class {    private tooltipElem: HTMLElement | null = null;    constructor(readonly view: EditorView) {      this.handleMouseMove = this.handleMouseMove.bind(this);      view.dom.addEventListener("mousemove", this.handleMouseMove);    }    handleMouseMove(event: MouseEvent) {      const pos = this.view.posAtCoords({ x: event.clientX, y: event.clientY });      if (pos === null) {        this.hideTooltip();        return;      }      // 現在位置に適用されているデコレーションを検査      const state = this.view.state;      const decorations = state.field(auditDecorationField, false);      let foundActive = false;      decorations?.between(pos, pos, (from, to, value) => {        foundActive = true;        this.showTooltip(event.clientX, event.clientY, from, to);      });      if (!foundActive) this.hideTooltip();    }    showTooltip(x: number, y: number, from: number, to: number) {      // 縦書き幾何補正      const isVertical = this.view.dom.classList.contains("mode-vertical");      if (!this.tooltipElem) {        this.tooltipElem = document.createElement("div");        this.tooltipElem.className = "cm-audit-tooltip-bubble";        document.body.appendChild(this.tooltipElem);      }      this.tooltipElem.textContent = "対立仮説：執事ボブ説と競合中";      if (isVertical) {        // 縦書き：カーソルの「左側（行送り先）」にツールチップを展開し、文字の視界を確保        this.tooltipElem.style.left = `${x - #### 6. 実装における留意点と例外ハンドリング
この設計をプロダクションへ投入するにあたり、以下の境界条件に対する配慮が必要と考えられます。
- マルチペイン・複数Viewの同期: スプリット画面で同一の EditorState を複数の EditorView で共有している場合、StateField で管理していれば全ての画面に同一の装飾が自動反映されますが、ホバーツールチップなどのView固有DOMは各ペインのインスタンスに閉じるようスコープを分離する必要があります。
- 不可視タグ（SourceToDisplayMap）との座標オフセットの整合: 内部タグ（{clue:...}）がエディタ上で折りたたまれている（折畳み装飾が適用されている）場合、内部バッファの論理オフセットと画面上の視覚オフセットに乖離が生じます。CM6の Decoration.mark は論理オフセット（doc 内の文字位置）に対して付与するため、折りたたみWidgetの内部に正しく埋没・追従するよう、デコレーションの適用レイヤー順序（prec.low や prec.high）を明示的に指定しておくことが推奨されます。
