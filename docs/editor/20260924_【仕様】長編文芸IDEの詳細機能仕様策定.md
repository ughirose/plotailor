##### 競合調停アルゴリズム
- 背景色（Background）の競合: Layer 1の指定色をベースとし、Layer 2が存在する場合は mix-blend-mode: multiply または赤色系グラデーション（linear-gradient）の境界ボーダーを重畳。
- 下線/装飾線（Line）の競合: 縦書き組版における行間干渉を防ぐため、Layer 2（波線）がLayer 0（点線）を完全マスク。物理事実の確認はホバーツールチップまたは右ペインで代替。
- マージンインジケータ（Gutter Pill）: 競合範囲の先頭位置（縦書きにおける上端外側）に、最上位レイヤーのアイコンバッジ（Layer 2の警告アイコン等）をスタック表示。

##### 手動加筆スコア Smanual​ の数理モデル
エンティティが「ユーザーによって丹念に作り込まれた設定」か「本文から自動抽出された一時トークン」かを判定するため、以下の評価関数を導入することが妥当と考えられます。
Smanual​=wl​⋅ln(Lnote​+1)+wf​⋅Nfields​+ws​⋅Isecret​+wr​⋅Nrelations​
- Lnote​: 設定ノートの総文字数（対数スケールで極端な長文の影響を緩和）
- Nfields​: ユーザーがデフォルト値から変更した属性フィールド数
- Isecret​: 最重要機密（SecretTruth）フラグの有無（1 or 0）
- Nrelations​: 他のエンティティとの関連リンク数
- 重み係数設定（推奨値）: wl​=1.2,wf​=2.0,ws​=5.0,wr​=1.5
- 判定閾値: θshelf​=4.0

#### ベクトル走査ロジックの設計
- 特定ASCII記号の1命令抽出: 改行（0x0A, 0x0D）、アノテーション開始符（@ = 0x40）、パイプ記号（| = 0x7C）などを i8x16.eq によって並列走査し、v128.bitmask を介して32ビット整数（下位16ビット有効）へ変換します。マスク値がゼロであれば、当該16バイト内に文構造の区切りが存在しないと判断し、インデックスを16バイト前進させます。

### 2. 差分更新（Incremental Parsing）アルゴリズムと木構造Rebase
長編全体（数十万字）の構文木をタイピングごとに全再構築することは、サブ2ms枠を逸脱する主因となります。編集箇所を含む最小の独立文脈単位（チャンク境界）のみを局所パースし、後続ノードは座標補正（Coordinate Rebase）で更新する戦略が合理的と考えられます。
 既存構文木: [Chunk 0: 安定] ── [Chunk 1: 編集対象 (Dirty)] ── [Chunk 2: 安定] ── [Chunk 3: 安定]                                       │                                       ▼ 再解析 & スキャナ終了状態の検証                           State_End == State_Next_Start ?                                ├── True ──► [Chunk 2以降はOffsetのみシフト (Rebase)]                                └── False ─► [Chunk 2へカスケード再解析を伝播]
#### アルゴリズム手順
- Dirty範囲の同定: エディタから渡される編集差分 EditDelta { from, to, insert_len } に基づき、影響を受ける葉ノード（Leaf Node）および親ブロックを同定します。
- 境界の拡大（Context Expansion）: 日本語の会話文（「……」）やルビ（｜……《……》）の未閉じ状態を考慮し、直前の「確定した改行」または「確定したブロック開始位置」まで解析開始点を巻き戻します。
- レキサー状態（Lexer State）の照合と伝播遮断: 各チャンクの終端におけるパサー状態（括弧ネスト深度、POVコンテキスト、TrFN有効フラグ等）をビットフィールドとして記録しておきます。再パース結果の終端状態が以前の状態と完全一致する場合、構文解析をそこで停止（Early Cutoff）します。
- Coordinate Rebase（相対座標の適用）: 後続する安定チャンクに対しては、木構造を維持したまま文字オフセット差分 Δ=insert_len−(to−from) を適用します。

### 3. 仮想シャドウバッファと不完全構文サニタイズ
#### 3.1 マルチバイト文字およびサロゲートペアの切断保護
IME変換中は、ローマ字入力の中途半端なASCII（例: k）、あるいは変換途中の不正なUTF-8シーケンスが一時的に発生する可能性があります。これを直接Wasm SIMDロード命令（v128_load）に引き渡した場合、パーサのクラッシュや不正メモリアクセスを引き起こすリスクが生じます。
このため、共有メモリへ書き込む直前に以下のビットマスク検査（UTF-8 Well-formedness check）をインラインで実施するアプローチが妥当と考えられます。
// Wasm内部または前段バッファにおけるUTF-8境界検査#[inline(always)]pub fn validate_utf8_boundary(bytes: &[u8]) -> usize {    if bytes.is_empty() {        return 0;    }    let mut safe_len = bytes.len();        // 末尾バイトがマルチバイト文字の途中（後続バイト不足）でないかを逆順走査    while safe_len > 0 {        let b = bytes[safe_len - 1];        if b & 0x80 == 0 {            // 1バイトASCII: 境界として安全            break;        } else if b & 0xC0 == 0xC0 {            // 先頭バイトを発見（0b110xxxxx, 0b1110xxxx, 0b11110xxx）            let needed = if b & 0xE0 == 0xC0 { 2 }            else if b & 0xF0 == 0xE0 { 3 }            else if b & 0xF8 == 0xF0 { 4 }            else { 1 };                        if (bytes.len() - (safe_len - 1)) < needed {                // 必要バイト数が足りていないため、この先頭バイトの手前までを安全境界とする                safe_len -= 1;            }            break;        }        // 0b10xxxxxx (後続バイト) の場合はさらに1バイト前を探索        safe_len -= 1;    }    safe_len}
#### 3.2 未完成トークン（Dangling Syntax）の誤検知抑制
日本語文芸における特有の入力パターンとして、ルビ記法（｜漢字《かん）やかぎ括弧（「台詞）の入力途中において、閉じ記号（》 や 」）が存在しない瞬間が不可避に発生します。
この状態を即座にエラーとして解釈すると、「構文エラーによる画面の激しい点滅」を招くため、以下の構文許容マスク（Heuristic Quarantine）を適用することが検討されます。
- 隔離規則 1: キャレット位置を含む現在行末までに閉じられていないルビ開始符（｜ または 《）が存在する場合、その行のパース結果を「IncompleteToken」としてマークし、Layer 2（POV機密漏洩監視）の検証対象から除外。
- 隔離規則 2: かぎ括弧（「）が開かれた直後の未確定入力中は、当該ノードの終了位置を仮に「キャレット位置」として扱い、後続テキスト全体を会話文として巻き込まないよう一時フェンス（Quarantine Fence）を挿入。
### 4. CodeMirror 6連携とDecorationフリーズ仕様

CodeMirror 6においては、トランザクションのアノテーション（Annotation）を検知し、Composition中の一切の装飾差分更新をスキップするトランザクションフィルタの導入が不可欠と考えられます。

### 5. IME保護機構の定量的評価とトレードオフ
本保護仕様を適用した場合における、安定性・リソース消費・執筆体感のトレードオフを検証します。

| 評価項目 | 保護機構なし（直接パース） | 保護レイヤー導入時（Proposed） | 考察と妥当性 |
| --- | --- | --- | --- |
| IME確定前の入力遅延 | 1.5∼4.2 ms（毎打鍵Wasm呼出） | ほぼ 0 ms（Wasm呼出を保留） | ブラウザのメインスレッド負荷が打鍵中に発生せず、高速入力時の取りこぼしが抑制される見込みです |
| 変換候補ウィンドウの安定性 | 低（DOM再構築による消失多発） | 極めて高い（DOM破壊ゼロ） | 装飾の再構築をフリーズさせることで、OSネイティブのIME表示との干渉が回避可能と考えられます |
| 未確定時のPOV警告即時性 | 即時（ただし誤検知を多数含む） | 確定時まで遅延（意図的抑制） | 未確定の入力途中で「POV違反」の赤波線が点滅する認知的ストレスを排除できるため、文芸用途では有利と推測されます |
| メモリオーバーヘッド | ゼロ | 軽微（Shadow Buffer保持用） | 数十バイトから数百バイト程度のバッファ保持に留まるため、実用上の負荷は極めて小さいと考えられます |

#### 実装上の注意点と境界条件
- 予期せぬフォーカス喪失時のリカバリ: Composition中にユーザーがマウスで別ペインをクリックしたり、ショートカットキーでダイアログを開いた場合、ブラウザによっては compositionend が正常に発火しないケースが存在します。エディタの blur イベントを捕捉し、強制的に COMMITTING または CANCELING 状態へ安全に遷移させるフェイルセーフが不可欠と考えられます。
- 長大な未確定文字列の扱い: 音声入力や長文一括変換などにより、未確定文字列が数千文字に及ぶケースでは、確定時（compositionend 直後）の差分パース処理が瞬間的にサブ2msの目標枠を超える懸念があります。この例外ケースにおいては、前述のCadence制御（Short Pause / Settling）と連携させ、1,000文字を超える一括確定時は即時同期を行わず、バックグラウンドのWeb Workerへ逃がすデグラデーション設計の併用が有効と推測されます。

User prompt: 数千文字の一括確定や貼り付けが発生した際、メインスレッドのサブ2msを維持しつつWeb Workerへ処理を逃がすデグラデーション設計の詳細仕様を策定してください。
Response: 大規模なペースト操作や長文の一括確定（音声入力、まとめ変換等）が発生した際、メインスレッドが構文解析でブロックされてサブ2msのレスポンス枠を逸脱することを防ぐには、「投機的座標シフト（Speculative Coordinate Shift）」による即時UI復帰と、「世代管理型Web Workerオフロード」による非同期解析を組み合わせたデグラデーション設計が有効と考えられます。
### 1. 処理振り分け基準（Threshold & Route Decision）
編集イベントが発生した際、差分サイズおよび構文構造の破壊度合いをO(1)で事前評価し、メインスレッド完結の「Fast Path」とバックグラウンドへ逃がす「Async Path」へ動的に分岐させます。

| 評価指標 | 閾値 | 判定理由と挙動 |
| --- | --- | --- |
| 挿入文字数 (ΔL) | ≥800 文字 | UTF-8展開時に約2.4KBを超過し、SIMDベクトル走査＋AST再構築が1.5ms境界に接近するため |

### 2. 投機的座標シフトとUI縮退表示（Degraded State）

### 3. Web Worker通信アーキテクチャと世代管理（Epoch-based Cancellation）
Workerへのデータ転送に伴う構造化複製（Structured Clone）の直列化遅延を排除するため、テキストデータは ArrayBuffer（Transferable Objects）または SharedArrayBuffer によるゼロコピー受け渡しを採用することが妥当と考えられます。
また、Workerがバックグラウンド解析を行っている間にユーザーが次の文字を入力する事象に対処するため、単調増加するエポックID（Epoch ID）による競合制御を導入します。
 メインスレッド (Epoch = 42)                 Web Worker (Dedicated)      │                                                │      ├─ [Paste発生: 3,000文字]                       │      ├─ ArrayBuffer転送 (Transferable) ──────────────►│      │                                                ├─ Narrative-Nano (Wasm) 実行      │  (解析中に入力継続: Epoch -> 43)               │      │                                                │      ├─ [新たなキー入力: 'あ']                        │      │                                                ├─ パース完了 (Nodes生成)      │◄─ 解析結果返却 (Epoch: 42) ───────────────────┤      │                                                │      ▼ [リコンサイル判定]  Current (43) > Payload (42)   └─► 破棄せず、差分履歴（Epoch 42->43）に基づき座標を補正（Rebase）して適用

### 4. 解析結果のリコンサイル（Reconciliation）アルゴリズム
Workerから構文解析結果が返却された際、エディタの状態が既に先へ進んでいる場合があります。この際、結果を一律破棄（Stale Drop）すると、長文ペースト直後の波線解析がいつまでも完了しない事態を招きます。
そのため、「未反映エポック間の変更ログを用いた座標リベース」を実行し、遅延して戻ってきた構文木を最新DOMへ統合する手順が有効と推測されます。
 Worker返却ノード (範囲: 1000 - 4000)    │    ▼ メインスレッド変更キュー (Epoch 42 -> 43: Offset 500 に 1文字追加) [Transform: Offset >= 500 のノード全座標に +1 加算]    │    ▼ 最新ドキュメントへアトミック適用 [CodeMirror DecorationSet の一括置換]
#### 状態遷移表

| 現在の状態 | イベント | ガード条件 | 遷移先 | 実行処理 |
| --- | --- | --- | --- | --- |
| Idle | 大規模編集検知 | ΔL≥800 | Degraded | 投機的シフト適用、WorkerへBuffer転送、保留装飾を設定 |
| Degraded | 追加打鍵（Typing） | - | Degraded | メイン側で通常編集。Epochをインクリメントし変更ログを保持 |
| Degraded | Worker完了応答 | res.epoch === currentEpoch | Idle | ノードバッファを直接DecorationSetへ変換・全レイヤー反映 |
| Degraded | Worker完了応答 | res.epoch < currentEpoch | Reconciling | 変更ログを適用してノード座標をRebase後、即時適用し Idle へ |
| Degraded | 別の大規模編集 | ΔLnew​≥800 | Degraded | 先行Workerタスクへ中断シグナル（Abort）を送出し新規タスク開始 |

#### 実装上の注意点
- SharedArrayBufferのクロスオリジン制約: より厳格なゼロコピーを実現するために SharedArrayBuffer を用いる場合、配信サーバ側で Cross-Origin-Opener-Policy: same-origin および Cross-Origin-Embedder-Policy: require-corp のヘッダー付与が必須となります。オフライン配信用デスクトップアプリ（Tauri等）ではカスタムプロトコルスキーム側でのヘッダーエミュレーション設定が必要となる点に留意が求められます。

#### 必須ヘッダーの仕様と影響範囲

| ヘッダー名 | 設定値 | 役割と動作仕様 | 潜在的な影響とトレードオフ |
| --- | --- | --- | --- |
| Cross-Origin-Opener-Policy (COOP) | same-origin | 該当ドキュメントを別オリジンのウィンドウから隔離し、参照コンテキストを分離 | window.open で開いた外部ウィンドウへの直接参照が切断されます |

### 2. TauriカスタムURIスキームハンドラ仕様（Rust実装）
Tauri（v2系アーキテクチャ想定）のIPC/アセット配信用プロトコルハンドラにおいて、リソース返却時にヘッダーを動的付与する実装方針を以下に示します。
// src-tauri/src/protocol.rsuse tauri::{    http::{header, Request, Response, ResponseBuilder, StatusCode},    AppHandle, Runtime,};use std::fs;use std::path::PathBuf;pub fn register_isolated_protocol<R: Runtime>(    app: &tauri::App<R>,    scheme: &'static str,    asset_root: PathBuf,) -> Result<(), Box<dyn std::error::Error>> {    app.register_asynchronous_uri_scheme_protocol(scheme, move |_app_handle, req, responder| {        let root = asset_root.clone();                // 非同期スレッドプールでファイル読み込みとヘッダー生成を実行        tauri::async_runtime::spawn(async move {            let response = handle_request(req, &root).unwrap_or_else(|err| {                ResponseBuilder::new()                    .status(StatusCode::INTERNAL_SERVER_ERROR)                    .header(header::CONTENT_TYPE, "text/plain; charset=utf-8")                    .body(err.to_string().into_bytes())                    .unwrap()            });            responder.respond(response);        });    })?;    Ok(())}fn handle_request(    request: Request<Vec<u8>>,    asset_root: &PathBuf,) -> Result<Response<Vec<u8>>, Box<dyn std::error::Error>> {    let uri_path = request.uri().path();    let relative_path = if uri_path == "/" || uri_path.is_empty() {        "index.html"    } else {        uri_path.trim_start_matches('/')    };    let file_path = asset_root.join(relative_path);    // ディレクトリトラバーサル防止の検証    if !file_path.starts_with(asset_root) {        return Ok(ResponseBuilder::new()            .status(StatusCode::FORBIDDEN)            .body(b"Access Denied".to_vec())?);    }    if !file_path.exists() {        return Ok(ResponseBuilder::new()            .status(StatusCode::NOT_FOUND)            .body(b"File Not Found".to_vec())?);    }    let mime_type = mime_guess::from_path(&file_path)        .first_or_octet_stream()        .to_string();    let content = fs::read(&file_path)?;    // クロスオリジン分離ヘッダーの網羅的注入    let mut builder = ResponseBuilder::new()        .status(StatusCode::OK)        .header(header::CONTENT_TYPE, mime_type.as_str())        .header("Cross-Origin-Opener-Policy", "same-origin")        .header("Cross-Origin-Embedder-Policy", "require-corp")        .header("Cross-Origin-Resource-Policy", "same-origin")        .header(            header::CONTENT_SECURITY_POLICY,            "default-src 'self'; script-src 'self' 'wasm-unsafe-eval'; style-src 'self' 'unsafe-inline'; img-src 'self' data: blob:; font-src 'self';"        );    // Wasmモジュール配信時は正確なMIMEタイプを保証    if file_path.extension().map_or(false, |ext| ext == "wasm") {        builder = builder.header(header::CONTENT_TYPE, "application/wasm");    }    Ok(builder.body(content)?)}
### 3. クライアント側の分離環境検証とフォールバック設計

#### 運用および設計上の留意点
- WebView2におけるキャッシュとスキームバインド: Windows環境のWebView2では、カスタムスキーム（例: app://）のセキュリティオリジンが適切に固定されていない場合、window.crossOriginIsolated が有効化されない事例が報告されています。Tauriの設定（tauri.conf.json）において、セキュリティヘッダーをIPC層だけでなく、全ローカルアセット配信エンドポイントに対して一律に反映させる設計が求められます。

### 2. Atomics同期プロトコルとノンブロッキング制御仕様
メインスレッドの処理ループを一切ブロック（休止）させない一方、解析アイドル時のWeb WorkerによるCPU浪費（ビジーループ）を防ぐため、「Worker側のみ Atomics.wait() で休止させ、メイン側は Atomics.notify() または requestAnimationFrame（rAF）ポーリングで駆動する」非対称モデルが適していると考えられます。

#### スレッド別制約と同期メカニズム
- メインスレッド（完全ノンブロッキング）:
  - 書き込み時: 空き領域容量が不足している場合（write_idx - read_idx >= CAPACITY）、ブロッキング待機は行わず、即座に「フレーム内ドロップ」または「Asyncフォールバック」へ退避。
  - 読み出し時: 毎フレームの描画契機（rAF）または打鍵ハンドラの冒頭で、Atomics.load(res_write_idx) と res_read_idx を比較し、差分が存在する場合のみノードを回収。
- Workerスレッド（選択的スリープ）:
  - Atomics.load(req_write_idx) と req_read_idx が一致した場合、Atomics.wait(worker_state_ptr, 0) を呼び出しスレッドを停止。OSレベルでのコンテキストスイッチによりCPU消費を抑制。

export class MainThreadBridge {  private ctrl: Int32Array;  private reqBuffer: Uint8Array;  private resBuffer: Uint8Array;  private textEncoder: TextEncoder;  constructor(private sharedBuffer: SharedArrayBuffer) {    this.ctrl = new Int32Array(this.sharedBuffer, 0, RingBufferLayout.HEADER_SIZE / 4);    this.reqBuffer = new Uint8Array(      this.sharedBuffer,      RingBufferLayout.REQ_BUFFER_OFFSET,      RingBufferLayout.REQ_BUFFER_SIZE    );    this.resBuffer = new Uint8Array(      this.sharedBuffer,      RingBufferLayout.RES_BUFFER_OFFSET,      RingBufferLayout.RES_BUFFER_SIZE    );    this.textEncoder = new TextEncoder();  }  /**   * 編集差分の書き込み（完全ノンブロッキング）   */  public pushEditRequest(from: number, to: number, text: string, epoch: number): boolean {    const write = Atomics.load(this.ctrl, RingBufferLayout.REQ_WRITE_PTR);    const read = Atomics.load(this.ctrl, RingBufferLayout.REQ_READ_PTR);    // 最大ペイロードサイズ + ヘッダー16バイト    const payloadBytes = this.textEncoder.encode(text);    const packetLength = 16 + payloadBytes.length;    // リングバッファの空き領域計算    const occupied = write - read;    if (RingBufferLayout.REQ_BUFFER_SIZE - occupied < packetLength) {      // バッファフル状態: ブロックせず即座にfalseを返却      return false;    }    // パケット書き込み (簡易スロット: [Length:4B, From:4B, To:4B, Epoch:4B, Text...])    const slotOffset = write & (RingBufferLayout.REQ_BUFFER_SIZE - 1);    const headerView = new DataView(this.sharedBuffer, RingBufferLayout.REQ_BUFFER_OFFSET + slotOffset, 16);        // バッファ終端を跨ぐ場合のフォールバック境界チェック    if (slotOffset + packetLength > RingBufferLayout.REQ_BUFFER_SIZE) {      // リング境界の分割処理、またはアライメント調整を実施    }    headerView.setUint32(0, packetLength, true);    headerView.setUint32(4, from, true);    headerView.setUint32(8, to, true);    headerView.setUint32(12, epoch, true);    this.reqBuffer.set(payloadBytes, slotOffset + 16);    // ポインタ更新 (Release セマンティクス)    Atomics.store(this.ctrl, RingBufferLayout.REQ_WRITE_PTR, write + packetLength);    // Workerがスリープ状態であれば復帰シグナルを発行    if (Atomics.load(this.ctrl, RingBufferLayout.WORKER_STATE_PTR) === RingBufferLayout.WORKER_STATE_SLEEPING) {      Atomics.store(this.ctrl, RingBufferLayout.WORKER_STATE_PTR, RingBufferLayout.WORKER_STATE_ACTIVE);      Atomics.notify(this.ctrl, RingBufferLayout.WORKER_STATE_PTR, 1);    }    return true;  }  /**   * レスポンスノードの回収（rAFタイミング等で非同期実行）   */  public pollParseResults(): Array<{ from: number; to: number; type: number }> | null {    const write = Atomics.load(this.ctrl, RingBufferLayout.RES_WRITE_PTR);    const read = Atomics.load(this.ctrl, RingBufferLayout.RES_READ_PTR);    if (write === read) {      return null; // 新規データなし    }    const slotOffset = read & (RingBufferLayout.RES_BUFFER_SIZE - 1);    const headerView = new DataView(this.sharedBuffer, RingBufferLayout.RES_BUFFER_OFFSET + slotOffset, 8);    const packetLength = headerView.getUint32(0, true);    const nodeCount = headerView.getUint32(4, true);    const nodes: Array<{ from: number; to: number; type: number }> = [];    const nodeDataView = new DataView(      this.sharedBuffer,      RingBufferLayout.RES_BUFFER_OFFSET + slotOffset + 8,      nodeCount * 16    );    for (let i = 0; i < nodeCount; i++) {      const offset = i * 16;      nodes.push({        from: nodeDataView.getUint32(offset, true),        to: nodeDataView.getUint32(offset + 4, true),        type: nodeDataView.getUint8(offset + 8),      });    }    // 読み取り完了を通知 (Release)    Atomics.store(this.ctrl, RingBufferLayout.RES_READ_PTR, read + packetLength);    return nodes;  }}

#### 潜在的なトレードオフと境界条件
- バッファオーバーラン時の縮退ポリシー: 長編小説の極端な一括置換（全置換等）でリングバッファの容量（2MB）を超過した場合、メインスレッド側で pushEditRequest が false を返します。この例外ケースでは、リングバッファへの投入を諦め、前章で策定した「世代管理付きTransferable ArrayBuffer」へ一時的にフォールバックさせるフェイルセーフ回路が有効と考えられます。
- Atomics.notifyの呼び出しコスト: メインスレッドから Atomics.notify() を頻繁に発行すると、ブラウザおよびカーネルの同期プリミティブによるコンテキストスイッチコスト（数マイクロ秒）が蓄積します。Workerが既に ACTIVE（処理中）状態である場合は Atomics.notify() をスキップする条件判定（if (worker_state === SLEEPING)）を設けることで、不要なシステムコールを削減できる見込みです。

### 1. ゼロコピー折り返し（Wrap-around）パディングアルゴリズム
#### 1.1 分割コピー問題と終端スキップ方式の比較
リングバッファ終端でデータが二分割されると、受信側のWasm SIMD命令（v128_load）が2つの断片を一度ローカルバッファへコピーして結合せざるを得ず、ゼロコピー性が失われます。これを回避するためのアプローチを比較検証します。
【二分割方式（コピー発生）】 バッファ末尾: [前半データ (100B)] ──(境界)──► バッファ先頭: [後半データ (100B)] ※ 受信側で連続領域へ memcpy するオーバーヘッドが発生【終端スキップパディング方式（ゼロコピー維持）】 バッファ末尾: [Sentinel Header (スキップ指示)] ──(境界)──► バッファ先頭: [完全な200Bデータ] ※ 常に連続した単一スライスとして参照可能

| 方式 | 連続参照性 | メモリ効率 | 実装複雑度 | レイテンシへの影響 |
| --- | --- | --- | --- | --- |
| 分割リングバッファ | 境界部で連続性が破綻 | 100%（パディングなし） | 高（読み出し側で2回に分けて処理） | 境界を跨ぐ際に memcpy が発生し、サブ2ms枠を圧迫するリスク |
| 終端スキップパディング | 常に100%連続（ゼロコピー） | 終端に最大パケット長分の空隙が生じる | 低（単一の境界チェックと番兵読み飛ばし） | ポインタ前進のみで完結（オーバーヘッド最小） |

WebAssembly側でSIMDロード命令を最速で実行するためには、メモリ断片化の軽微なコストを許容してでも「終端スキップパディング方式」を採用することが合理的と考えられます。
#### 1.2 パディング挿入と読み飛ばしのステートマシン
 [書き込み要求 (Len: L)] ───► 残り容量 >= L ?                                   ├── Yes ──► 終端までの空き >= L ?                                   │               ├── Yes ──► [通常パケット書き込み]                                   │               └── No  ──► [Sentinelパディング書き込み] ──► [先頭(Offset 0)へ書き込み]                                   └── No  ──► [Buffer Full: 即時リジェクト (ノンブロッキング)]
##### パケットヘッダー仕様（8バイト固定）
- type (u8): 0x01 = DATA, 0xFF = SENTINEL_WRAP（スキップ指示）
- flags (u8): SIMDアライメントや構文メタデータ
- epoch (u16): 世代管理番号
- length (u32): パケット全体の総バイト数（ヘッダー8バイト ＋ ペイロード）
##### 送信側（Producer）のポインタ制御手順
- 現在の書き込みオフセット Woff​=W & (C−1) を算出（C は2のべき乗のバッファ長）。
- バッファ終端までの残余長 Rtail​=C−Woff​ を評価。
- Rtail​<PacketLength の場合：
  - 終端の隙間に type = 0xFF、length = R_{tail} のダミーパケットを書き込み。
  - W を W+Rtail​ だけアトミックに進め、先頭（Woff​=0）から本データを書き込み。
- 受信側（Consumer）は type == 0xFF を検知した瞬間に、そのパケット長分だけ読み取りポインタ R を前進させて先頭へジャンプ。

#### 3.2 メインスレッド側: 終端パディング付きProducer実装
export class ZeroCopySpscProducer {  private ctrlView: Int32Array;  private ringBytes: Uint8Array;  private textEncoder: TextEncoder;  constructor(private wasmSharedMemory: WebAssembly.Memory) {    const rawBuffer = wasmSharedMemory.buffer as SharedArrayBuffer;    this.ctrlView = new Int32Array(rawBuffer, HybridBufferConstants.CONTROL_BLOCK_OFFSET, 64);    this.ringBytes = new Uint8Array(      rawBuffer,      HybridBufferConstants.REQ_BUFFER_OFFSET,      HybridBufferConstants.REQ_BUFFER_SIZE    );    this.textEncoder = new TextEncoder();  }  /**   * 境界パディングを挟みつつテキスト差分を連続領域としてゼロコピー投入   */  public pushEditPacket(from: number, to: number, text: string, epoch: number): boolean {    const textBytes = this.textEncoder.encode(text);    // パケット全体長: ヘッダー(8B) + 差分メタデータ(8B: from 4B, to 4B) + UTF-8文字列    const payloadLength = 8 + textBytes.length;    const totalPacketLength = 8 + payloadLength;    const write = Atomics.load(this.ctrlView, 0); // req_write_ptr (Index 0 = Offset 0x000)    const read = Atomics.load(this.ctrlView, 16); // req_read_ptr (Index 16 = Offset 0x040)    const capacity = HybridBufferConstants.REQ_BUFFER_SIZE;    const mask = HybridBufferConstants.REQ_BUFFER_MASK;    // バッファ全体の空き容量を検証    if (capacity - (write - read) < totalPacketLength) {      return false; // 容量超過    }    let writeOffset = write & mask;    const tailSpace = capacity - writeOffset;    // 終端に収まらない場合、Sentinelパディングを書き込んで先頭へ折り返し    if (tailSpace < totalPacketLength) {      // 残余容量がSentinelヘッダー（8B）未満の場合はみ出さないよう配慮      if (capacity - (write - read) < totalPacketLength + tailSpace) {        return false; // パディング込みの空き容量が不足      }      // 終端にスキップヘッダーを刻印      const sentinelView = new DataView(        this.ringBytes.buffer,        HybridBufferConstants.REQ_BUFFER_OFFSET + writeOffset,        tailSpace      );      sentinelView.setUint8(0, HybridBufferConstants.PACKET_SENTINEL_WRAP);      sentinelView.setUint8(1, 0);      sentinelView.setUint16(2, epoch, true);      sentinelView.setUint32(4, tailSpace, true);      // 書き込みポインタを終端分スキップ      const nextWrite = write + tailSpace;      Atomics.store(this.ctrlView, 0, nextWrite);      writeOffset = 0; // 次のデータは先頭から    }    // 本パケットの書き込み（常に完全に連続した領域へ展開される）    const targetAbsoluteOffset = HybridBufferConstants.REQ_BUFFER_OFFSET + writeOffset;    const headerView = new DataView(this.ringBytes.buffer, targetAbsoluteOffset, 16);    headerView.setUint8(0, HybridBufferConstants.PACKET_DATA);    headerView.setUint8(1, 0);    headerView.setUint16(2, epoch, true);    headerView.setUint32(4, totalPacketLength, true);    headerView.setUint32(8, from, true);    headerView.setUint32(12, to, true);    this.ringBytes.set(textBytes, writeOffset + 16);    // アトミックにポインタを前進 (Release)    const finalWrite = (writeOffset === 0 ? write + tailSpace : write) + totalPacketLength;    Atomics.store(this.ctrlView, 0, finalWrite);    // Workerが停止中なら起床シグナルを送出    if (Atomics.load(this.ctrlView, 64) === 0) { // worker_state (Index 64 = Offset 0x100)      Atomics.store(this.ctrlView, 64, 1);      Atomics.notify(this.ctrlView, 64, 1);    }    return true;  }}
#### 3.3 Rust / Wasm側: ゼロコピーConsumerおよびSIMD直接解析
Worker内のWasmコアは、受信したリングバッファ内のメモリアドレスを一切のバッファコピーを経由せず、直接スライスポインタとして解釈してSIMDベクトル走査に流し込みます。

 // Offset 0x000    let req_read_atomic = &*(ctrl_ptr.add(16) as *const AtomicU32); // Offset 0x040    let global_epoch_atomic = &*(ctrl_ptr.add(80) as *const AtomicU32);    let write = req_write_atomic.load(Ordering::Acquire);    let mut read = req_read_atomic.load(Ordering::Relaxed);    if write == read {        return 0; // データなし    }    let mut read_offset = (read as usize) & REQ_BUFFER_MASK;    let packet_ptr = base_memory_ptr.add(REQ_BUFFER_OFFSET + read_offset);    let packet_type = *packet_ptr;    let packet_len = *(packet_ptr.add(4) as *const u32);    // Sentinelパディングの検出: 終端を読み飛ばして先頭へジャンプ    if packet_type == PACKET_SENTINEL_WRAP {        read += packet_len;        req_read_atomic.store(read, Ordering::Release);                // 再帰またはループで先頭パケットの読み出しへ継続        read_offset = (read as usize) & REQ_BUFFER_MASK;    }    let actual_packet_ptr = base_memory_ptr.add(REQ_BUFFER_OFFSET + read_offset);    let payload_len = *(actual_packet_ptr.add(4) as *const u32) - 16;    let text_ptr = actual_packet_ptr.add(16); // 16バイト境界アライメント済みテキスト    // Narrative-Nano: コピーを介さずWasm線形メモリ上の連続ポインタをSIMDで直走査    let delimiter_mask = scan_delimiters_simd(text_ptr, payload_len as usize);    // 読み出し完了をコミット    let total_consumed = *(actual_packet_ptr.add(4) as *const u32);    req_read_atomic.store(read + total_consumed, Ordering::Release);    delimiter_mask}#[inline(always)]unsafe fn scan_delimiters_simd(ptr: *const u8, len: usize) -> u32 {    let mut mask_accum = 0u32;    let chunks = len / 16;    let nl = i8x16_splat(0x0A);    for i in 0..chunks {        let chunk = v128_load(ptr.add(i * 16) as *const v128);        let cmp = i8x16_eq(chunk, nl);        mask_accum |= i8x16_bitmask(cmp) as u32;    }    mask_accum}
### 4. トレードオフ評価とアーキテクチャ妥当性の検証

| 評価指標 | 独立SAB ＋ 構造化複製転送 | 提案方式（統合共有メモリ ＋ 終端パディング） | 技術的考察と判定 |
| --- | --- | --- | --- |
| テキスト解析着手レイテンシ | 0.2∼0.6 ms（複製とデシリアライズ） | ≈0 ms（ポインタ参照のみ） | メインスレッドがSABに書き込んだ瞬間にWasmが同一アドレスを直接走査可能なため、サブ2ms維持に対して理想的と考えられます |

#### 境界条件とフェイルセーフ
- 巨大パケットによるバッファ溢れ: 数MB規模の原稿が一括ペーストされた場合、パケット長がリングバッファの半分（2MB）を超過し、折り返しパディング計算が破綻するリスクがあります。パケット長が一定閾値（例: 64KB）を超える場合は本リングバッファを使用せず、前章で策定した「Worker生成型フォールバック（Transferable ArrayBuffer）」へとルーティングを切り替える防御コードが必須となります。
- ブラウザ間での WebAssembly.Memory 共有サポート状況: Chromium系（V8）およびFirefox（SpiderMonkey）では共有Wasmメモリが長期にわたり安定稼働している一方、WebKit（Safari）環境では一部のバージョンにおいて共有Wasm線形メモリに対するスレッド間Atomics動作に細かな仕様差異が見られる場合があります。実行時機能判定（Feature Detection）によって共有メモリモードとメッセージパッシングモードを透過的に切り替える安全策が推奨されます。

Response: Web Workerがメモリ不足（OOM）やWasmパニック、あるいは無限ループ等の予期せぬ要因で異常停止した場合、メインスレッドとWorkerが共有するSharedArrayBuffer上のSPSC（単一生産者・単一消費者）制御ブロックには、未確定のポインタや矛盾した状態フラグが取り残されるリスクがあります。
この状態を放置すると、メインスレッド側の書き込みが永久にブロックされるか、新規に起動したWorkerが不正なメモリアドレスを読み込んで即座に再クラッシュする連鎖障害を招く懸念が生じます。

### 1. 異常検知アーキテクチャ（二重監視メカニズム）
Workerの停止には「OS/ブラウザによるプロセスキル（受動的検知）」と「Wasm内での無限ループやデッドロック（能動的検知）」の2つの形態が存在するため、イベントハンドラとAtomicsウォッチドッグを併用する二重化構成が有効と考えられます。
 ┌─────────────────────────────────────────────────────────────┐ │ メインスレッド監視レイヤー                                   │ │  ├─ 受動検知: worker.onerror / worker.onmessageerror        │ │  └─ 能動検知: Watchdog (rAF毎に Atomics タイムスタンプ検査)  │ └──────────────────────────────┬──────────────────────────────┘                                │ 異常シグナル検知 (Timeout > 50ms)                                ▼ ┌─────────────────────────────────────────────────────────────┐ │ リカバリコントローラ (Recovery Controller)                   │ │  1. worker.terminate() で旧スレッドを完全隔離・強制停止      │ │  2. 制御ブロック（SPSCポインタ）のサニティチェックとリセット │ │  3. 新規Workerのスポーンと同一SABの再バインド                │ │  4. エディタ装飾の同期フォールバック（Cold Resync）          │ └─────────────────────────────────────────────────────────────┘
#### 監視パラメータと判定基準

| 検知方式 | 監視対象 | 判定条件 | 検出可能な異常 |
| --- | --- | --- | --- |
| 受動監視 | worker.onerror | エラーイベントの発火 | 未捕捉の例外、Wasmランタイムパニック、スクリプト評価失敗 |
| 受動監視 | worker.onmessageerror | デシリアライズ失敗 | メモリアクセス違反による通信破損 |
| 能動監視 (Watchdog) | worker_heartbeat | 最終更新から経過時間 >100 ms | Workerスレッド全体の完全停止、過負荷による応答途絶 |
| 能動監視 (Task Lease) | task_started_at | 処理中（PARSING）のまま経過時間 >50 ms | Wasm正規表現の破綻、極端に重い構文ループ、デッドロック |

### 2. 共有メモリ破損パターンの分類と判定マトリクス
Workerが任意のタイミングで突発停止した場合、制御ヘッダー（ControlBlock）は以下の不整合状態に陥る可能性があります。
【正常状態】 0 <= (req_write_ptr - req_read_ptr) <= REQ_BUFFER_SIZE【破損状態 A: ポインタ逆転 / 不正アライメント】 req_read_ptr > req_write_ptr  または  ptr % 4 != 0【破損状態 B: 処理中放置 (Stale Lock)】 worker_state == PARSING  かつ  Heartbeat 更新停止【破損状態 C: パケットヘッダーの分断 (Torn Packet)】 packet_len == 0  または  packet_len > REQ_BUFFER_SIZE
#### 健全性検証アルゴリズム（Sanity Check）
新規Workerを接続する前、またはリカバリトリガー時に、制御変数が数学的・論理的境界内に収まっているかを以下の条件式で検証します。
- ポインタ境界条件:0≤(Wreq​−Rreq​)≤Creq​∧(Wreq​(mod4)=0)∧(Rreq​(mod4)=0)
- レスポンスポインタ境界条件:0≤(Wres​−Rres​)≤Cres​∧(Wres​(mod4)=0)∧(Rres​(mod4)=0)
- 世代整合性:packet_epoch≤global_epoch
上記のいずれか1つでも満たされない場合、バッファポインタの復元は不可能とみなし、キューの安全な一括フラッシュ（Drain）を実行します。
### 3. 自己修復ステートマシンとリカバリシーケンス
リカバリ処理中はエディタ本文への打鍵が継続している可能性があるため、メインスレッドの入力を阻害しないアトミックな修復遷移が必要です。
 [NORMAL] ─── 異常検知 (Timeout / Error) ───► [QUARANTINE] (Worker強制破棄)    ▲                                                │    │                                                ▼ [STABILIZED] ◄── Cold Resync 完了 ── [REBUILDING] (制御ヘッダー再初期化 & (装飾同期復元)                        (新Worker起動)   保留キューフラッシュ)
#### 状態遷移仕様

| 現在の状態 | トリガー | 遷移先 | 実行処理 |
| --- | --- | --- | --- |
| NORMAL | ハング検知（>50 ms）または onerror | QUARANTINE | 即座に worker.terminate() を実行。エディタの装飾更新を一時凍結（Freeze） |
| QUARANTINE | プロセス終了確認 | REBUILDING | 制御ブロックのAtomics変数をアトミックリセット。global_epoch をインクリメント |
| REBUILDING | 新規Workerインスタンス化 | STABILIZED | 同一SABを渡してWorker初期化。現在のエディタ表示範囲全体を「Cold Resync」タスクとしてキューイング |
| STABILIZED | 初期パース結果の受領 | NORMAL | 保留されていた装飾を一括適用し、定常動作へ復旧 |

### 5. 妥当性検証とトレードオフの検討

| 評価項目 | 全面リブート方式（SABごと再割り当て） | 提案方式（ポインタ再同期 ＋ スレッド再起動） | 技術的考察 |
| --- | --- | --- | --- |
| 復帰所要時間（MTTR） | 80∼250 ms（メモリ確保・再初期化） | 5∼15 ms（スレッド起動のみ） | メモリ割り当てを回避することで、タイピング中の視覚的引っ掛かりを最小化できる見込みです |
| 未処理データの扱い | キュー内データ完全喪失 | 読み取りを書き込みポインタへ追いつかせて安全破棄 | エディタが正本テキストを保持しているため、パース差分の破棄は許容され、Cold Resyncで即時補填が可能です |
| 連続クラッシュ耐性 | 考慮なしの場合ブラウザがクラッシュ | 3回連続失敗で安全モード（Linter完全停止）へ移行 | 特定の構文パターンによる「ポイズンピル（無限パニック）」からメインスレッドを保護可能と考えられます |
| 実装オーバーヘッド | 軽微 | 中程度（WatchdogとAtomicsヘルスチェックの維持） | 50ms間隔のタイマー走査は数マイクロ秒で完了するため、CPU負荷は極めて小さいと推測されます |

#### 運用上の留意事項
- ポイズンピル（特定の入力による確定クラッシュ）の隔離: 特定の文字シーケンス（例: 未対応の極長サロゲートペアや正規表現のバックトラック誘発構文）が入力されたことでWorkerが即死した場合、Cold Resyncで全く同一のテキストを再投入すると即座に再クラッシュするリスクがあります。consecutiveFailures がインクリメントされた直後のResyncでは、問題箇所の構文木解析を一段階粗いフォールバック（字句解析のみ、または装飾スキップ）へ自動でダウングレードする設計が妥当と考えられます。
- ブラウザ間での terminate() の即時性: ほとんどのモダンブラウザにおいて worker.terminate() は同期的にスレッドリソースを切り離しますが、内部的なWasmインスタンスの破棄完了までには僅かなGCタイムラグが存在する場合があります。同一のSABを新規Workerへ即座に渡しても、OSレベルの排他ロックによる競合は生じない構造（Atomics変数による論理分離）となっているため、実用上の安全性は保たれると評価されます。
