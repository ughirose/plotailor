#### 2. 「真実の源泉（SSOT）」をめぐる構成上のジレンマ
アーキテクチャを決定づける最も根本的な論点は、「本文テキストが正本なのか、それとも背後の世界モデルが正本なのか」という主権の所在にあります。
##### A. Text-Centric（本文主権型）
- 構成: 本文テキストを唯一の正本（SSOT）とし、イベントや因果モデルは「本文から抽出された派生キャッシュ」として扱う。
- 特性: 小説執筆ツールとしての直感性に優れ、Git等のテキストベースのバージョン管理と親和性が高い傾向があります。
- 懸念点: 本文に書かれていない暗黙の前提（裏設定、作外で進行する別動隊の動きなど）をモデル空間に保持しにくく、テキスト削除時に裏の因果グラフまで道連れで破壊されやすい脆弱性を内包します。
##### B. Model-Centric（世界線主権型）
- 構成: Layer 0〜2 の因果グラフおよび状態遷移ログを正本とし、本文テキストは「特定の視点・順序で切り取られたレンダリング結果（View）」に過ぎないとみなす。
- 特性: ゲーム開発（CRPGのシナリオ設計等）やTRPG設定構築に近く、タイムラインの分岐や客観的事実の整合性維持が強固になりやすいです。
- 懸念点: 作家が「本文の筆の乗りに任せて書く」自由が奪われ、事前にイベントノードを定義してから本文を書くという、執筆の摩擦（Friction）を生む恐れがあります。
##### 検証の着地点：Event-Sourcing による双方向調停構成
このジレンマに対しては、「本文中の明示的タグから抽出されたイベント」と「GUIや設定から直接投入された客観イベント」を同一のイベントストア（StateDeltaEvents[]）へ集約し、エディタのアンカーが消失してもイベント自体は「本文未割当（Unassigned Event）」として生き残るイベント・ソーシング的調停モデルが妥当と考えられます。
#### 3. 多層オーバーレイ構造（Layer 0 / 1 / 2）の依存と浸透
確定した3層のデータモデルが、どのような依存方向と情報フィルタリングの関係にあるかを整理します。

##### レイヤー間の浸透ルール
- 下層は上層を知らない（一方向依存）: Layer 0（物理）は、Layer 1（因果）の伏線都合や Layer 2（視点人物の主観）によって物理法則を曲げてはならない。物理矛盾を許容する場合は「Axiom（世界観公理）の例外」として下層自体を更新する。
- 上層は下層を部分観測する（認識の歪み）: Layer 2 は、Layer 0/1 の客観事実のうち「視点人物が知覚できるサブセット」のみを射影し、地の文として展開する。

#### 1. 本文パーサーが担う責務と境界の再定義
本文パーサーの役割は、単に「テキストから文字列を抜き出すこと」にとどまりません。エディタ（表現空間）の不安定で流動的な文字列を、因果モデル空間（Layer 0/1）が要求する「厳密で決定論的なイベント」へと変換するプロトコル変換器（Anti-Corruption Layer）として機能する必要があります。
[ エディタ (CodeMirror 6) ]   │   │ Raw Text Changes (1打鍵ごとの破壊と再構築)   ▼┌──────────────────────────────────────────────────────────┐│ 本文パーサー境界 (Parser & Staging Boundary)             ││  ├── 1. 差分トークン抽出 (Token Scanning)                ││  ├── 2. 構文確定判定 (Syntactic Boundary / Debounce)      ││  └── 3. 幽霊イベント防止フィルタ (Draft Quarantine)      │└──────────────────────────────────────────────────────────┘   │   │ 確定した StateDeltaEvents[] ＆ TextAnchors[]   ▼[ 因果モデル空間 (Layer 0: Projection / Layer 1: DAG) ]
この境界において解決すべき中核的な課題は以下の3点に集約されます。
- タイピング途中の「構文の不完全性」への耐性ユーザーがタグを入力している途中（例: ｜アリス《char: まで打った状態）で解析が走ると、不正なIDや未完のイベントが発行され、後続の Projection Engine をクラッシュさせる、あるいは不必要なキャッシュ破棄を引き起こすリスクがあります。
- 文字座標（Raw Offset）とイベントIDの紐付け（Anchor Binding）パースによって生成されたイベントは、本文中の「どの文字区間（[from, to]）」に根ざしているかを保持しなければならず、前後のテキスト編集によってその座標がリアルタイムに追従（Rebase）される必要があります。
- パース処理自体の計算負荷（Latency Isolation）長編小説（数万〜数十万文字）において、1打鍵ごとに全文を再スキャンすると UI スレッドの 16ms フレームバジェットを圧迫します。
#### 2. 構文解析方式の比較とトレードオフ
本文中のタグ（ルビ、座標、伏線記法など）を検出するアプローチとして、主に3つの方式が検討できます。

| 方式 | 機構 | メリット | 懸念点 / トレードオフ | 適合性の判定 |
| --- | --- | --- | --- | --- |
| A. 全文正規表現スキャン  (Full Regex Scanner) | トランザクションごとに正規表現で全文を走査 | 実装が最も平易で、記法ルールの追加が容易 | 文字数 N に対して O(N)。数万文字規模でタイピング遅延の主因となりやすい | プロトタイプ向き / 本番不適 |
| B. 差分行スキャナ  (Line-based Dirty Scanner) | tr.changes が及んだ変更行（Dirty Lines）のみを正規表現で局所再走査 | 実装複雑度を抑えつつ、タイピング時は O(1)〜O(行長) で動作可能 | 複数行を跨ぐブロック記法（例: {scene ... }）の開始・終了判定で境界の管理が複雑化する | 有力な候補（第1段階） |
| C. 増分構文木解析  (Lezer Incremental Parser) | CodeMirror 6 ネイティブの構文解析木（LR/GLR）を利用し、構文木を差分更新 | 不完全な構文でもエラー耐性（Error Recovery）を持ち、極めて高速かつ構造的 | 独自構文の文法定義（.grammar）の学習・保守コストが高く、文法変更の小回りが効きにくい | 将来的な本命（第2段階） |

##### 開発フェーズに応じた現実的な選択肢
初期段階においては、Lezerの文法コンパイル環境を整える工数を避け、「B. 変更行を起点とする差分スキャナ」を採用しつつ、ブロックの整合性を保つ最小限のステートマシンを組むのが、開発速度と実行性能のバランスにおいて合理的である可能性が高いと考えられます。
#### 3. タイピング途中の一時状態を隔離する「二層ステージング」
モデル空間（Projection Engine / Causal DAG）に不完全なデータが流れ込むのを防ぐため、パーサー内部に「Draft（下書き）」と「Committed（確定）」の二層ステージング境界を設ける設計が有効と推測されます。
[テキスト入力] ──▶ [即時抽出: Draft Stage]                         │                         ├── 構文エラー / 未完成タグ ──▶ 破棄（モデルへ送らない）                         │                         └── 構文完全 ──(確定判定)──▶ [Committed Stage]                                                         │                                                         ▼ モデル空間へ送出                                                    (StateDeltaEvents)
##### 確定判定（Commit Condition）の論理規則
以下のいずれかの条件を満たした瞬間にのみ、Draft から Committed へと状態を昇格させます。
- 構文の完全性（Syntactic Completeness）:閉じ括弧（》 や ]、}）が入力され、トークンとしての終端が辞書的に成立していること。
- 入力休止の検知（Temporal Debounce）:文字入力が 200〜300ms 停止したこと（IME 確定直後など）。
- キャレットの離脱（Spatial Departure）:ユーザーが当該タグの範囲外へカーソルを移動、または別行へジャンプしたこと（入力を終えて次の執筆に移ったとみなせる）。
この隔離機構を挟むことで、「タグの入力途中に一文字打つたびにチェックポイントが全破棄され、地図のマーカーが点滅する」といった不快な挙動を構造的に遮断できます。
#### 4. 記法セット（Syntax Primitives）のミニマム設計
作家の自然な執筆フローを妨げないため、過度にプログラミング言語的な記法を避け、小説執筆で一般的に用いられるルビ記法等を自然拡張した構文設計が求められます。
1. キャラクター登場 / 存在   彼 は ｜ アリス 《 char:alice 》 と 呼 ば れ て い た 。   （親文字「アリス」を表示し、内部的に char:alice を紐付け）2. 物理移動 / 座標指定   一行 は 王都 ［ @loc:capital, 35.68, 139.76 ］ へ と 足 を 踏 み 入 れ た 。   （地名エイリアスおよび緯度経度のマッピング）3. 伏線の設置と回収   暖炉の奥には、古びた真鍮の鍵 ｛ plant:brass_key ｝ が隠されていた。   ... (数百行後) ...   取り出した真鍮の鍵 ｛ payoff:brass_key ｝ を鍵穴に差し込む。
##### 抽出されるメタデータとアンカーの対応関係
パーサーがテキストを走査した結果、1つのタグから以下の2つの対をなすオブジェクトが同時に生成されます。
- TextAnchor（エディタ側）:{ id: 'ev_123', rawFrom: 14, rawTo: 38 }本文中の位置追従、インライン装飾、Diffプレビューの基準点となる。

Layer 0（物理・時空）が「客観的に何が起きたか」を扱い、Layer 1（因果・ドラマ）が「なぜそれが起きたか」を記述するのに対し、Layer 2 は「それは誰によって、どのように知覚され、読者へいかなる順序と制約で語られるか」を調停する階層と定義できます。
物語論（ナラトロジー）における「ファブラ（Fabula: 作中時系列に沿った客観的出来事）」と「シュジェ（Sjuzhet: 本文テキストに現れる語りの順序や表現）」の乖離を構造化し、小説特有の表現技法をシステム側で扱えるようにする役割を持ちます。
[ Layer 0: 物理・客観事実 (Fabula) ]   - 世界内で発生した物理現象（誰がどこで何を話したか、何が起きたか）          │          ▼ 観測フィルター（知覚・物理的限界）[ Layer 1: 因果・動機グラフ (Causal DAG) ]   - 行動理由と伏線連鎖          │          ▼ 演出・認知的歪み（語り手の選択・隠蔽・錯誤）[ Layer 2: 言説・演出層 (Sjuzhet / Epistemology) ]   ├── ① 視点制限 (POV Constraints): 誰の目を通して語られているか   ├── ② 認知の地平 (Epistemic Horizons): 誰がその事実を知っていて、誰が知らないか   └── ③ 語りの順序 (Discourse Ordering): 回想・予見による時系列の再編成
#### 2. Layer 2 を構成する3つの主要プリミティブ
このレイヤーをソフトウェア的に形式化する場合、以下の3つのモデル要素が必要になると考えられます。
##### A. 視点コンテキスト（POV Context）
本文の特定の区間（シーン、章、あるいは段落）において、どの視点規範が適用されているかを規定するスコープ定義です。
- 一人称（First-Person）: 語り手自身（char:protagonist）の五感・内面のみが記述可能。
- 三人称一元視点（Third-Person Limited）: 地の文は客観調だが、知覚・内面描写は特定の単一キャラクター（焦点化人物: Focalizer）に限定される。
- 三人称多元視点（Multi-POV）: シーンごとに焦点化人物が切り替わる。
- 三人称全知視点（Third-Person Omniscient）: 原則として任意の人物の内面や遠隔地の事象を記述可能だが、現代作劇では意図しない全知化（視点ブレ）が問題視されることが多い。
##### B. 認知の地平（Epistemic Horizon / 知識状態）
情報が作中世界内をどのように流通しているかを追跡するためのグラフ構造です。ある客観事実（Fact F）に対し、各主体の知識状態を Kc​(t)（時刻 t において主体 c が F を知っているか否か）としてモデル化します。
[ 客観事実 F: 城の地下に抜け道がある ]   ├── キャラクターA: 既知 (K_A = True) ──▶ Layer 0 で現地を探索済み   ├── キャラクターB: 未知 (K_B = False) ──▶ まだ報告を受けていない   └── 読者 (Reader): 既知 (K_Reader = True) ──▶ 第1章でAの視点を通じて描写済み
この「登場人物間の知識差」および「登場人物と読者の知識差（劇的アイロニーや叙述トリック）」を明示的に区別することが、作劇支援における核となります。
##### C. 語りの順序写像（Discourse Mapping / アナクロニー）
Layer 0/1 ではイベントが「作中時間（Tick）」順に並びますが、本文テキストでは回想（Analepsis）や予見（Prolepsis）によって過去や未来の出来事が前後して語られます。
- 出来事時間（Story Tick）: 作中世界における客観的な時間軸（Layer 0）。
- 語り位置（Discourse Offset）: 本文中の文字位置または章節番号。
Layer 2 は、本文のアンカー区間と Layer 0 の各 Tick の間に「非線形な対応関係（Mapping）」を保持する責務を負います。
#### 3. 検出対象となる「言説的破綻（Discourse Anomalies）」の分類
Layer 2 の導入によって自動検証が可能となる作劇矛盾は、以下のようなパターンに整理できます。

| 不整合パターン | 定義・発生条件 | 検出のための判定ロジック | 重要度 |
| --- | --- | --- | --- |
| 視点逸脱  (POV Breach / 視点ブレ) | 三人称一元視点や一人称において、焦点化人物以外の「他者の心情」や「不可視領域」が地の文で断定されている | Subject(MentalState)=Focalizer かつ POV Mode=Limited | Warning / Error |
| 認知漏洩  (Epistemic Leak) | 主体が知り得ないはずの情報に基づいて意思決定や行動を起こしている（神の視点の混入） | 行動の前提条件 F∈/KActor​(t)（伝達経路・観測イベントの欠落） | Error (因果・認知複合) |
| 語りの時系列矛盾  (Narrative Anachronism) | 回想シーン内において、その回想時点より未来の出来事があたかも過去の既知事実として語られている | Tick(ReferencedEvent)>Tick(RecalledScene) | Error |
| 未開示前提の言及  (Premature Exposition) | 読者にとって初出の専門概念や裏設定が、開示イベントを経ずに既知のものとして唐突に解説される | 読者知識セット KReader​(Offset)=∅ なのに前提描写が欠如 | Suggestion |

#### 4. レイヤー間の浸透と情報伝達パイプライン
Layer 0、1、2 がどのように連携してこの検証を完結させるか、依存とデータの流れを検証します。
[ Layer 0: 物理・時空 ]   - 空間座標 (X, Y) と視線・聴覚範囲   - 情報伝達イベント（会話、手紙、通信）の物理的到達          │          ▼ 「誰が何を知覚可能か」の物理境界を提供[ Layer 2: 知識伝播エンジン (Epistemic Propagation) ]   - 会話の場に同席していた人物の K_c を True に更新   - 伝達経路のない隔絶された人物の K_c を False に凍結          │          ▼ 「この行動は知識的に合法か」を検証[ Layer 1: 因果グラフ (Causal Graph) ]   - 「裏切りを知ったから攻撃した」という因果エッジに対し、     Layer 2 が「その時点で裏切りを知る経路が存在したか」を照合
##### 例：物理と認知の連動
- キャラクターAとBが座標 [35.68, 139.76] の同一部屋で密談を行う（Layer 0）。
- 同席しているAとBの知識セットに「秘密計画」が追加される（Layer 2）。
- 部屋の外にいるキャラクターCの知識セットには追加されない（Layer 0 の遮蔽・距離判定）。
- 後続のシーンでキャラクターCが「Aの秘密計画を阻止するために動く」場合、Cへの情報伝達イベント（盗聴、告白、密告など）が中間に存在しない限り、Layer 2 検証器が「認知漏洩（Epistemic Leak）」として警告を発出する。
#### 5. 課題と自律的検証：形式化と創作の自由度のバランス
Layer 2 のアーキテクチャを固めるにあたっては、以下の設計的トレードオフを慎重に見極める必要があります。
- 「信頼できない語り手（Unreliable Narrator）」の許容:語り手が意図的に読者に嘘をつく、あるいは記憶違いをしている演出の場合、システムがそれを一律に「矛盾」と判定してしまうと表現の幅が狭まります。したがって、Layer 2 の指摘は「物理的な絶対エラー」ではなく、「意図的な演出か、無自覚なミスかを作家に確認させるフラグ（Annotation）」として振る舞うのが妥当と推測されます。
- 自然言語からの視点・心情の抽出難易度:「アリスは悲しそうに見えた（外形知覚：合法）」と「アリスは悲しかった（内面断定：視点ブレ）」の差は、単純なタグ解析だけでは判定が難しく、LLM による構文・文脈解析への依存度が高まります。ルールベースで判定可能な「空間的・情報的な知覚境界」と、AIに委ねる「文体・叙述のニュアンス」の境界を明確に切り分けることが求められます。
この Layer 2 の基本構成（視点・認知・語り順）を踏まえることで、WorldCraft の3層オーバーレイの論理構造は概念的に一通り網羅された形となります。
このまま「3. フロントエンド統合レイアウト（各層を単一画面に束ねるドッキング・UI構成）」へ進むか、あるいは Layer 2 の認知伝播の具体的なデータ構造についてさらに深掘りするか、どちらの考察に進みますでしょうか。

#### 1. 「事実（Fact）」と「信念（Belief）」の分離：認識論的論理（Epistemic & Doxastic Logic）の導入
Layer 0 で確定する客観的出来事をそのまま「知識」として配るアプローチをとると、「嘘」「勘違い」「噂による情報の歪み」「偽の証拠」といった作劇上の重要な要素が扱えなくなる懸念が生じます。
したがって、古典的な認識論理（Modal Epistemic Logic）の考え方を援用し、「作中の客観事実（World Proposition）」と、「各主体がそれをどう認識しているかという信念状態（Doxastic State）」を峻別する構成が有効と推測されます。
[ Layer 0: 客観事実 (World Proposition: P) ]  例: P_01 = { id: "fact_assassination_plot", trueValue: true, originTick: 100 }       │       ▼ 各観測・伝達イベントによる主観への射影┌─────────────────────────────────────────────────────────────┐│ Layer 2: 主体ごとの認識状態 (Epistemic State of Agent C)     ││   ・Status:                                                 ││       - UNKNOWN       : まったく知らない                    ││       - KNOWN_TRUE    : 正しい事実として確信している        ││       - FALSE_BELIEF  : 偽情報を真実だと思い込んでいる (誤認)││       - SUSPECTED     : 疑っている (確信度: 0.1〜0.9)       ││   ・Source:                                                 ││       - DIRECT_SIGHT  : 直接目撃した                        ││       - TESTIMONY     : 誰かから聞いた (伝達経路の追跡)      ││       - INFERENCE     : 状況証拠から推論した                │└─────────────────────────────────────────────────────────────┘
##### 知識状態（Knowledge State）の推移モデル
主体 c の事実 p に対する認識 Kc​(p) は、単純な真偽値（Boolean）ではなく、以下のような多値状態を持つモデルとして定義することが妥当と考えられます。

| 状態値 | 意味 | 作劇上の使途 |
| --- | --- | --- |
| UNKNOWN | その命題の存在自体を知らない | 情報格差、サプライズの前提 |
| KNOWN_TRUE | 客観的に正しく、本人も正しく知っている | 確実な情報に基づく合理的な行動 |
| FALSE_BELIEF | 客観的には偽（または歪曲された情報）を真実と誤認 | 罠に嵌まる、誤解による対立、悲劇のトリガー |
| SUSPECTED | 真偽を決めかねている（疑惑・仮説段階） | 探偵の推理過程、疑惑のサスペンス |
| DISBELIEVED | 真実を告げられたが「嘘だ」と拒絶している | 警告の無視、認知バイアス |

#### 2. 知識伝達グラフ（Epistemic Propagation Graph）の4経路
主体間で情報が流通する経路は、Layer 0 の物理制約および Layer 1 の因果関係から導出される以下の4つの伝播チャネルとして抽象化できると考えられます。
1. 直接知覚 (Direct Observation)   [Layer 0 物理事象] ──(視線・聴覚範囲内)──▶ [Agent A: KNOWN_TRUE (直接目撃)]2. 対人伝達 (Interpersonal Relay)   [Agent A] ──(会話・尋問・密談)──▶ [Agent B: KNOWN / FALSE_BELIEF]        │        └── ※ A が「嘘」をつくミューテーションを挟むことで情報が変質3. 物的証拠・記録 (Artifact Stigmergy)   [Agent A] ──(手紙・日誌・足跡)──▶ [Item X] ──(発見・読解)──▶ [Agent C]        │        └── ※ 時空を超えた非同期の伝播（Tick が大きく離れる）4. 状況推論 (Logical Deduction)   [K_c(p_1) = TRUE] ∧ [K_c(p_2) = TRUE] ──(推論ルール)──▶ [K_c(p_3) = SUSPECTED]
##### 伝達時の「情報の歪み（Distortion）」のモデル化
情報が A から B へ伝達される際、常に完全な複製が行われるとは限りません。以下のパラメータを伝達リンク（TransmissionLink）に持たせることで、伝言ゲームの破綻を構造的に捉えられる可能性があります。
- 忠実度（Fidelity / Veracity）: 情報をそのまま伝えたか、一部を隠蔽・誇張・捏造したか。
- 確信度減衰（Confidence Decay）: 又聞きを重ねるごとに「確信（KNOWN_TRUE）」から「噂・伝聞（SUSPECTED）」へと状態が格下げされる度合い。
#### 3. 状態爆発を抑える「疎結合差分ツリー」のデータ構造
単純に「全キャラクター数 C× 全事実数 F× 全作中時間 T」の直積空間を保持すると、状態数が指数関数的に増大し、ブラウザのメモリやWorker間通信のバジェットを容易に超過するリスクがあります。
この課題を回避するため、Gitのコミットツリーや永続データ構造（Persistent Data Structures）に類似した差分ログ方式を採用することが検討されます。
// 事実（命題）の基本単位export interface EpistemicFact {  id: string; // 例: "fact:king_murdered"  category: 'event' | 'identity' | 'secret' | 'spatial';  canonicalTruth: boolean; // 客観的な真偽  originTick: number;      // 発生時刻  description: string;}// 認識状態の変更差分（Event Sourcing 的なDelta）export interface EpistemicDelta {  factId: string;  agentId: string; // 'char:alice', または読者を表す 'agent:reader'  previousState: EpistemicStatus;  newState: EpistemicStatus;  confidence: number; // 0.0 〜 1.0  sourceChannel: 'observation' | 'dialogue' | 'letter' | 'deduction';  witnessEventId: string; // どの Layer 0 イベントによって伝播したか}// Tickごとの累積スナップショット管理（疎結合マップ）export interface EpistemicSnapshot {  tick: number;  // agentId -> (factId -> State) の疎配列（変化があったエージェントのみ記録）  agentKnowledge: Map<string, Map<string, EpistemicRecord>>;}
##### スナップショットのインクリメンタル解決
Layer 0 で採用した K=250 チェックポイント方式と同様に、認知状態も「起点からの全量累積」ではなく、「知識の獲得・変質イベントが発生した Tick でのみ差分（EpistemicDelta）を記録し、特定 Tick の状態は直近チェックポイントからのリプレイで即座に展開する」 アーキテクチャが、メモリ消費と再計算レイテンシの面で優位性を持つと推測されます。
#### 4. 視点（POV: Point of View）制約の数理・論理判定
Layer 2 の最も重要な応用先である「視点ブレ・視点逸脱（POV Breach）」の自動検知を、曖昧な自然言語解釈ではなく集合論的な包含関係として形式化できるかを検証します。
[ 本文の特定シーン S ]  ├── 焦点化人物 (Focalizer): Agent F  ├── 語りモード (POV Mode): THIRD_PERSON_LIMITED (三人称一元視点)  │  ▼ 当該シーン内で言及・描写される命題集合: { p_1, p_2, ..., p_n }
##### 判定規則の定式化
シーン S において記述されている任意の事象・命題 p に対し、以下の論理式が成立しているかを検証します。
∀p∈DescribedProps(S),IsDescribable(p,F,tS​)
ここで IsDescribable の成立条件は、事象 p の種別（客観的外形か、主観的内面か）によって厳密に分岐します。
- 内面心理・感情の記述（Internal Monologue / Mental State）: 対象が主体 A の内面である場合、焦点化人物 F と一致していなければならない。Subject(p)=F（A=F の場合、「A は悲しかった」は視点ブレとして Error、「A は悲しそうに見えた/俯いた」は外形観測として許容）
- 空間的知覚の記述（Sensory Observation）: 事象 p が発生した物理座標 (xp​,yp​) に対し、焦点化人物 F のその時刻における知覚コーン（Perceptual Cone）内に入っていなければならない。Distance(Pos(F,t),Pos(p,t))≤PerceptualRadius(F)∧¬IsOccluded(F,p)
- 過去・外部事実の言及（Exposition / Fact Recall）: 地の文で語られる設定や過去の事実 p は、その時刻時点で焦点化人物の知識集合に含まれていなければならない。p∈KF​(tS​)
この判定式を適用することで、「その場にいないはずの人物の行動を地の文が勝手に語ってしまう」「焦点化人物が知らないはずの敵の真名を地の文で名指ししてしまう」といった初歩的かつ致命的なミスを、幾何計算と知識集合の照合によって決定論的に検出できる可能性が示唆されます。
#### 5. 読者認知（Reader Knowledge）と「叙述トリック・劇的アイロニー」の調停
小説において非常に高度な作劇技法である「読者だけが知っている（劇的アイロニー）」または「読者だけが騙されている（叙述トリック / 信頼できない語り手）」をシステムが誤検知してしまわないための自律的な設計検証が求められます。

##### 「信頼できない語り手（Unreliable Narrator）」の例外モデル
もし語り手が読者に対して意図的に嘘をついている場合、語りのテキストから抽出される p と、Layer 0 の客観的事実 ¬p が正面衝突します。
これをシステム側で破綻とみなさないためには、Layer 2 のメタデータとして「語り手の歪曲フラグ（narrativeDistortion）」を明示的に許容する構造が必要です。
- 通常モード: 本文の描写は Layer 0 の客観的事実と一致しなければならない（不一致は執筆ミス・破綻として検知）。
- 歪曲モード（Unreliable Mode）: 焦点化人物の FALSE_BELIEF、あるいは意図的な DECEPTION（虚偽の語り）が設定されている区間では、客観事実との衝突を「Error」ではなく「演出意図（Stylistic Device）としてのマーク」へダウングレードする。
#### まとめと構造的インサイト

##### リサイズ追従の技術的制約（Invalidation Lifecycle）
ペインのリサイズバーをドラッグした際、内部の Leaflet や D3 SVG はブラウザ標準のレイアウト変更を自動検知して再描画することができません。
- Leaflet: コンテナサイズ変更時に map.invalidateSize() を呼ばないとタイルが欠落する。
- D3 (SVG): ビューポートの clientWidth 変化に応じて scaleLinear の range を再計算する必要がある。
これを解決するため、各ペインのラッパーに ResizeObserver をマウントし、requestAnimationFrame または 100ms 程度のデバウンスを介して内部コンポーネントへリサイズシグナルを伝播させる調停層 が必須になると考えられます。

#### 2. 発火元ガード（Origin Guard）による循環イベント防止機構
複数コンポーネントが同一のストアを購読する場合、コンポーネントAの変更 → ストア更新 → コンポーネントBの追従 → コンポーネントBからストアへの再ディスパッチという無限ループが発生するリスクが伴います。
これを構造的に遮断するため、ストア内部に「発火元ガード（Origin Guard）」を組み込み、自身が原因となったイベントのループバックを弾く設計が有効と推測されます。
